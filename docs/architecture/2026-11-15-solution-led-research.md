# 围绕交付方案组织研究

用户已确认“选定方案—针对性取证—检查方案一致性”的优化方向。本设计将其落在现有 Planner、取证循环、Writer 和最终审查中；不增加常驻 Agent、检索提供商、模型调用阶段或全局预算，不处理无关工作区改动。

## 根因与取舍

此前五轮北京实测表明：查询先于具体方案，多个可选景点变成必查义务；需求 ID 分配完整却没有对应检索词；Writer 重新决定行程，最终审查只自由描述问题，交通票种与实际路线脱节也可能通过。

只继续加提示词改动小，但无法检查方案是否跨阶段传递；增加方案 Agent 和独立裁判会增加调用与编排复杂度。采用同一次 Planner 的结构化暂定方案，并复用现有审查调用。模型依然负责语义判断，宿主负责引用范围、需求映射、检查项完整性与 partial 状态，二者不能混同。

## 数据与链路

新增可选 `DeliveryPlan`：`approach`（选定路径）、`assumptions`（最多 4 条）、`outline`（最多 6 个具体交付步骤）、`evidence_needs`（最多 6 个需求 ID 与短检索词的对应）、`consistency_checks`（最多 6 条跨步骤检查）。它是可修改的方案假设，不是事实、用户授权或工具指令；科研事实查询等任务可为空。

Planner 先确定一条可执行主线，减少未选候选，再生成需求及每项的实际检索词。方案中的需求 ID 必须对应封存事实需求，重编号同步转换，重复或未知引用局部拒绝方案，不破坏独立合法的旧查询。

controller 存在合法方案时，以 `evidence_needs` 生成分支：每个需求有实际查询，最多原有任务数，每分支最多两条查询。超出容量时显式降级，不静默丢需求；保留原始问题和来源限制。旧规划数据没有方案时维持既有路径。

方案进入研究状态、取证简报、缺口补查、研究结果、Writer 及最终审查，支持 checkpoint 往返与旧结果读取。复用这些结构的旧模式传递方案；分支分配变更限 controller。

Writer 从方案形成完整答案，取证不支持时可删除或替换方案步骤并说明取舍，不能为维持方案捏造事实。最终审查除了原文支持，还逐项检查方案的费用/资源合计、人数或单位口径、步骤依赖、日程/可用性，以及方案使用的服务是否覆盖全部实际步骤。具体检查来自所选方案，不绑定北京或旅游领域。

最终审查返回每个检查项的 `check_id`、`status=passed|unresolved` 和 `reason`。宿主要求原有检查项恰好各一次；缺漏、重复或伪造编号在现有一次格式修复内纠正。`unresolved` 阻止完整完成，修正后的正文须保留限制；不得以一句“有引用”代替一致性检查。passed 是模型判断，并非宿主证明。

方案任务使用精简的专用审查策略，不再叠加全部科研、字段层级和实现机理规则。预算通过同次审查的可选 `budgets` 返回结构化数据：每表固定scope/unit，最多16行，行含价格上下限、数量、分摊和verified/reference/estimate/unpriced分类。宿主用Decimal按行计算、四舍五入到两位后加总并渲染；正文可引用同一总额。未计价不能填0，必需未计价项保留partial和明确提示。自由书写的重复小计改为引用预算表，避免展示格式反复消耗模型调用。价格真假、单位选择和方案依赖仍由取证及模型判断，不能由算术正确推出完整可执行。

## 实施计划（顺序执行，TDD）

- [x] 方案契约与解析：创建 `domain/delivery.py`、`strategies/delivery_planning.py`；测试非法引用、ID 重编号及可选数据局部降级；再接入 `seal_initial_plan` 与 Planner 指令。
- [x] 针对性分支：在 controller 初始化根据有效 evidence_needs 分组，构造 task_briefs/search_queries；集成测试通过实际 controller 启动取证，检查酒店、饮食、交通等独立需求均有查询，预算和用户约束保持。全部种子也写入可恢复的 typed task，无 task_briefs 时不丢第二条查询。
- [x] 端到端传递：更新三种状态、ResearchOutcome、各 finalize、简报和 checkpoint allowlist；测试结果序列化、重入清空、分支和响应上下文，旧结果仍可读取。范围审查排除需求时同步重编号查询引用。
- [x] 一致性审查：创建 `responses/consistency.py` 中的检查结果契约/校验；扩展已有 review 调用和 Writer 上下文。测试遗漏检查项不能完成、未解决依赖导致 partial；费用表由 `responses/budgets.py` 宿主计算，路线语义仍是模型判断；不增加成功路径模型调用。
- [x] 验证与审阅：相关回归、全量后端、改动范围 diff 检查与自审；同模型、同额度执行北京问题及另一类方案任务，保留全部试验原文、方案、用量和检查结果，人工检查实际答案。

验收不以测试数或 completed 为准：方案确实先于搜索；每项独立事实有查询；Writer 和审查收到相同暂定方案；一致性检查不漏项，未解决事项保持 partial；实际回答覆盖路线、住宿、餐饮、交通及预算，不能再拿地铁票覆盖未包含的远郊往返。保留检索、模型判断与报价时效的现实限制。

## 实施中确认的恢复问题

首轮北京实跑出现“后续窗口没显示旧来源→来源重置为uncertain→旧发现消失”，与方案先行仍不能稳定成稿有关。修复为在 controller 上增量保留未被本轮实际显示、此前已接受的发现；再次从证据库校验生命周期、版本、哈希和引用。被本轮明确拒绝或原文变更的发现仍剔除。模型跨轮复用 finding ID 时给保留项稳定独立 ID，不覆盖本轮结果；旧 coverage 不复用，缺口仍按本次评估计算。

controller 不再因合法的来源拒绝重审同批材料：宿主剔除被拒绝支持并归一覆盖，接着补查缺口。格式和未经授权的来源限制保留原有修复机会；legacy 默认修复策略保持。最终审查例子统一为完整有效 JSON，补充安全的格式修复事件，不记录模型原始输出。

最终后端回归：1652 passed、1 deselected、33 warnings，59.58秒。较早一轮出现一次SQLite后台线程清理警告，后续未复现，未对其作修复归因。新机制的确定性回归通过，实测仍有语义缺口：宿主能检查检查项是否齐全并确定预算表算术，不能证明模型的passed、价格或单位选择正确。

真实验收共保留北京3次、监控方案2次完整取证试验，另对同一研究材料进行了隔离的真实成稿/审查试验，各阶段结果均保留。最终同材料复核仍为partial，但北京已修正主线顺序，预算表与正文引用由宿主计算，缺价项不伪装成已核实费用。方案链路已落地，完整事实和一致性质量尚未全部通过。原始答案、检查结果、全部中间试验及局限见[实测报告](../benchmarks/2026-11-15-solution-led-research/README.md)。
