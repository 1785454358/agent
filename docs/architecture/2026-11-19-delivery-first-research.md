# 以报告交付为中心的减法建议

日期：2026-11-19。本文依据用户最新目标重新取舍：先减少运行机制，让研究结束后稳定交付有用且诚实的报告。此前 lean 修订版作为风险参考，不把其中新增类型、逐项门禁和多阶段协议全量建设作为本轮目标。本次为源码调研与设计建议，没有修改运行代码，也没有重新跑其他项目推断准确率。

## 1. 调研结论

| 项目 / 固定版本 | 实际行为 | 借鉴与边界 |
|---|---|---|
| [GPT-Researcher 标准报告](https://github.com/assafelovic/gpt-researcher/blob/6f998577d547b1e54ec662dac63583aa11e3b84b/gpt_researcher/skills/writer.py) | 根据已有 context 写报告，没有先检查每个用户需求都已 covered。context 全空时返回明确的资料不足说明。 | 研究与交付解耦，已有资料可以形成报告；不能把空资料硬写成长篇“有来源”的报告。这里不代表它的所有扩展模式都没有 review。 |
| [Open Deep Research](https://github.com/langchain-ai/open_deep_research/blob/1b7d2e80db9faa586165c60e09096dbbfd483a64/src/open_deep_research/deep_researcher.py) | 主管达到迭代上限、没有工具调用或发出 ResearchComplete 时结束研究；主图随后进入 final_report_generation，使用 notes 生成报告。 | 时间/轮次到限仍转写作，不用全事实覆盖作为研究退出前提。其主管、分支、压缩与重试本身也有复杂性，不照搬整套架构；写作仍可能失败。该仓库目前已归档，作为设计样本而非依赖升级建议。 |
| [dzhng/deep-research](https://github.com/dzhng/deep-research/blob/1f8f3e285bbc23e80b98a66a64effab9069f3ad4/src/deep-research.ts) | 按 breadth/depth 研究；失败的查询分支返回空结果；汇合 learnings 与 URLs。[CLI](https://github.com/dzhng/deep-research/blob/1f8f3e285bbc23e80b98a66a64effab9069f3ad4/src/run.ts)随后写报告或答案。 | 借鉴失败隔离、简单累计与明确终止。只累计字符串结论和末尾 URLs 不保证逐条可追溯，不照搬这种来源弱绑定，也不照搬无材料仍要求长篇写作。 |

上述代码支持的共同结论是“研究停止与报告生成解耦”，不支持“任何问题都能答对或任何服务故障都能成功”。本地原文与提交信息保存在 `.local-artifacts/lean-delivery-research-20261119/`。

## 2. 产品目标

在模型及必要服务正常可用时，研究不充分、局部分支失败、达到研究预算，均应进入报告阶段，给出已经支持的结论、建议与明确限制。用户取消、写作服务不可用、来源非法或不能形成任何有效交付，仍如实处理，不把异常字符串当成研究成功。

界面分别表达两件事：报告是否已交付；研究依据是否充分。复用现有状态与 `research_sufficiency` 表达，不增设另一套权威状态机。若采用“已交付”的 completed 语义，只用于明确版本化的新流程；旧记录不批量重标，质量评测也不能把 completed 当正确率。

“资料有限但有用的报告”应回应原问题，包含已有结论、来源、条件/假设以及尚不能确认的部分。只有一句“没查到”、空文本、错误堆栈或堆放几个标题，不算实质报告；完全无资料时应给明确限制说明，不假装完成可靠研究。

## 3. 唯一主流程

```text
理解问题与简短计划 → 有限搜索/阅读 → 用已有材料写报告 → 必要检查/一次就地修订 → 交付
```

- 研究按问题主要维度推进，达到足够材料、剩余预算阈值或轮次上限就结束；没有逐条事实全通过门禁。
- 局部工具失败记入限制，保留其他分支成果；不吞掉用户取消和授权失败。
- 为最终写作预留预算；不能把全部调用、输入和时间消耗在研究及核验上。
- 正文能说什么由实际资料决定。缺一个事实影响对应结论的表述，不清空整份回答，不把“本次未核实”升级成“规范没有规定”。
- 普通问答不强制附加一套模型审查。包含代码、硬约束或高风险具体建议时，可做一次短审查并就地修订；不重新启动全局研究。审查辅助字段不完整不应直接抹掉有效正文。
- 保留原文与短引，writer 和必要 reviewer 使用同一份实际材料快照，取消互相独立的重复裁剪。复用现有 Evidence、ReadEvidenceAnchor、引用校验和内部 State 交接，先不建设新的证据 DSL/大材料领域模型。

## 4. 真正的删除与保留清单

| 动作 | 具体对象 |
|---|---|
| 从生产研究循环拿掉 | 每轮 `run_evidence_evaluation`、全 required 覆盖完成门禁、由缺口驱动的反复全局重规划。覆盖指标可留在离线评测。 |
| 随前一项删除 | `evaluation_delta` 的 full/delta/reused 账本、研究核验快照/保留规则，以及只为它们服务的恢复状态。保留基础版本/hash 校验。 |
| 合并 | 三策略和 controller 的重复编排，只留一个共用调度主干；三模式仅保留固定工作、依赖推进、独立并行的真实差异。 |
| 合并 | 阅读、研究核验、写作各自重建的摘要/窗口，只交接一次实际原文材料。 |
| 收缩 | 多层 witness/修复协议、自动追加字段缺口、辅助审查记录门禁；保留简单必要检查，不强迫用户问题进入事实/设计四类门禁体系。 |
| 保留 | 搜索/抓取/阅读工具、EvidenceStore、来源权限、URL 校验、引用与版本坐标、总预算、usage、工具执行账本、取消与恢复。 |

以上是运行职责删除清单，不是立即整文件删除清单。被金额计算、历史读取或其他有效功能共用的函数保留。先替换调用路径，再删无依赖算法，避免在原系统旁边长期增加第四套引擎。

## 5. 最小落地顺序与验收

1. 冻结当前实际代码及 3 个复杂样本，保留原始回答与成本；不要仅 tag 未包含工作区修改的 HEAD。
2. 在现有共同主干中旁路研究全覆盖 evaluator，让有预算的正常研究结束后必到 writer；保留原题、来源限制、真实阅读材料与写作预算。先验证报告正常产生，不同时建设新门禁。
3. 统一 writer/reviewer 实际材料交接，去掉重复裁剪和辅助协议导致的整篇降级。保留一次必要修订，不增加另一套恢复管理器。
4. 验证三模式及取消/恢复，然后删除已经旁路的重复算法和状态；未迁移的活动任务、历史解码有清楚边界后再删对应文件。

先用 HTTP、Python 3.11、跨语言各一次观察“是否能交付实质报告”，再补单跳、资料不足、单支失败、预算到限、互相矛盾材料的回归。候选稳定后才扩大重复样本，不把开发阶段调过的题当独立测试。

必须同时检查：报告交付率、人工语义质量、来源/约束违例、调用与 token、剩余独立机制数量。报告正常完成但 POST 条件错误仍计质量失败；有用且诚实的有限报告也不该仅因未知事实被计为运行失败。没有重跑前不预报节省比例或成功率。

减法是否成立的标准：生产路径没有逐轮事实核验循环、没有 full/delta/reused 账本、没有三套重复研究算法；有一个明确进入最终写作的共同路径。单纯更名 lean、新加类型而旧机制仍运行，不算完成减法。
