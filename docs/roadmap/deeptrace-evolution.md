# DeepTrace 演进路线图

- 状态：阶段 1 待实施
- 更新日期：2026-08-29
- 目标：从最小可运行的 CLI 单 Agent 开始，逐步演进为具有证据链、验证、记忆、产品化和系统评测能力的 Deep Research Agent
- 设计依据：[DeepTrace 从零演进式构建设计](../superpowers/specs/2026-08-29-deeptrace-evolution-design.md)
- 当前实施计划：[DeepTrace 阶段 1：CLI 单 Agent 实施计划](../superpowers/plans/2026-08-29-stage-01-cli-single-agent.md)

## 1. 路线图的使用方式

DeepTrace 采用纵向演进式构建。每个阶段先解决一个已经出现的工程问题，形成可运行、可测试、可讲解的版本；只有通过本阶段门禁后，才进入下一阶段。后续阶段不能用来掩盖当前阶段尚未跑通的问题。

仓库中的内容分成两条互相隔离的轨道：

- **正式项目**：由学习者按照阶段文档手动创建和修改。Codex 在未获明确授权时不创建 `backend/`、`frontend/`、正式数据库迁移、正式配置或正式测试。
- **参考实现**：保存在 `reference_implementation/`，是每个阶段可独立运行的完整快照，只在学习者卡住时用于对照。参考实现不导入正式项目，也不能成为正式项目的运行依赖。

每个阶段至少交付：手动搭建文档、隔离参考实现、自动化测试、真实问题验收方法和清晰的 Git 提交点。正式项目必须由学习者亲手复现，不能把复制参考实现等同于完成阶段学习。

## 2. 九阶段总览

| 阶段 | 核心能力 | 可验证产物 | 对应岗位能力 |
|---|---|---|---|
| 1 | CLI 单 Agent + 搜索 + 抓取 | 真实两工具闭环 | Tool Calling、Agent loop、工程基础 |
| 2 | 工具层工程化 | 重试、超时、缓存、限流、SSRF 防护 | 工具套件与交付质量 |
| 3 | Agent 编排与模块拆分 | Planner/Researcher/Writer 工作流 | 规划执行、Agent 系统设计 |
| 4 | Evidence Store | Claim、Evidence、Source 可追踪 | RAG、数据建模、可追溯性 |
| 5 | Verifier | 引用覆盖、蕴含、冲突、时效检查 | Agent 评估与可靠性 |
| 6 | Memory | 会话记忆、研究记忆、用户偏好 | Memory 机制 |
| 7 | Deep Research 强化 | 查询改写、停止条件、并发与预算 | 专业领域 Agent |
| 8 | 产品化 | API、Web UI、任务状态与可观测性 | AI 原生应用落地 |
| 9 | 系统评测与开源对比 | 固定数据集、消融、基线对比 | 评估体系、论文复现能力 |

## 3. 阶段 1：CLI 单 Agent + 搜索 + 抓取

### 本阶段为什么现在做

先用最少概念跑通 Agent 的核心消息闭环。模型负责决定何时调用工具，宿主程序负责白名单、参数校验、真实网络执行、工具结果回填和终止控制。学习者必须先看懂一次完整的 `assistant tool_calls → role=tool → assistant final answer` 消息序列，后续的编排、证据和记忆才有可靠基础。

### 本阶段交付与验收

- 一个同步运行的 CLI 单 Agent。
- 只提供 `search_web` 与 `fetch_webpage` 两个工具。
- 使用 OpenAI-compatible Chat Completions Tool Calling、真实 Tavily、HTTPX 与 Trafilatura。
- 默认最多 8 次模型调用；搜索结果最多 5 条；网页正文最多 20,000 字符。
- 搜索摘要只用于发现候选网页。最终来源只允许来自本次成功抓取的 URL 集合。
- `uv run pytest -v` 直接执行真实 LLM、真实 Tavily 和真实公开网页测试。

### 本阶段明确不做

阶段 1 不引入 LangChain、LangGraph、Multi-Agent、Planner/Researcher/Writer 拆分、Evidence Store、Verifier、Memory、数据库、FastAPI、Web UI、PDF 解析、登录态或浏览器自动化。重试、缓存、完整 DNS/重定向 SSRF 防护也留给阶段 2。

### 阶段 1 门禁

只有以下条件全部满足，才能进入阶段 2：

1. “今天 AI Agent 领域有哪些热点新闻？”和“调研当前字节跳动 Agent 开发岗位的招聘要求，并给出来源。”两个真实验收问题都能触发搜索和抓取。
2. 报告来源只来自本次成功抓取的网页，不能把未抓取的搜索摘要当作来源。
3. `uv run pytest -v` 在真实凭据下全部通过，不存在 Fake、Mock、Stub、预录响应或离线降级。
4. 凭据缺失时测试明确失败；日志、异常、测试输出和报告中没有 API Key、Cookie 或 Token 泄漏。
5. 学习者能够解释一次完整消息序列，包括 `tool_calls`、`tool_call_id`、`role=tool` 回填和最终停止条件，而不只是运行参考实现。

## 4. 阶段 2：工具层工程化

### 本阶段为什么现在做

阶段 1 已证明模型能够通过两个工具完成闭环，接下来优先解决真实网络的不稳定性与安全边界。工具层稳定后，上层编排才能复用一致的结果结构和错误语义。

### 本阶段交付与门禁

- 搜索、抓取、注册与分发职责拆分。
- 统一搜索结果和网页文档结构，增加 URL 规范化和去重。
- 增加超时、有限重试、缓存、限流、响应大小限制、DNS 与重定向链 SSRF 防护。
- 面对重复结果、超时、重定向、危险 URL 和网页失败时仍有稳定的结构化结果。
- 阶段 1 的真实两工具闭环继续通过，新增故障与安全场景测试全部通过。

### 本阶段明确不做

不引入 Planner/Researcher/Writer、Multi-Agent、Evidence Store、Verifier 或 Memory；单 Agent 行为保持不变。浏览器自动化、登录网站和 PDF 解析仍不进入范围。

## 5. 阶段 3：Agent 编排与模块拆分

### 本阶段为什么现在做

工具接口稳定后，复杂研究问题开始暴露“一个循环同时负责规划、研究和写作”的职责混杂。此时拆出 Planner、Researcher、Writer，学习结构化规划与顺序执行，能让后续证据模型接入清晰的生产和消费边界。

### 本阶段交付与门禁

- 模型客户端、Prompt、状态、运行事件、工具注册与 Runner 职责清晰。
- Planner 生成结构化研究任务，Researcher 逐项搜索和抓取，Writer 汇总报告。
- 形成可追踪的 ResearchPlan、ResearchTask 和 RunState。
- 规划执行流程在真实问题上可复现；某项研究失败时能形成明确的部分结果，而非静默丢失。
- 阶段 1、2 的工具与真实验收行为无回退。

### 本阶段明确不做

不建立 Evidence Store，不运行 Verifier，不持久化 Memory，也不追求多 Agent 并发。即使未来可能采用 LangGraph，本阶段先把框架无关的模块契约和顺序工作流做清楚。

## 6. 阶段 4：Evidence Store

### 本阶段为什么现在做

有了明确的研究任务和报告生成边界后，才能准确回答“某条结论由哪段网页内容支持”。这一阶段把网页、证据片段和结论从自然语言上下文中提升为可检查的数据结构。

### 本阶段交付与门禁

- 建立 `Source → Evidence → Claim` 及关联关系，保留 URL、抓取时间、定位信息和证据文本。
- Researcher 保存来源和可定位证据，Writer 只读取满足发布边界的 Claim。
- 证据图可导出为 JSON；任意报告事实能够回溯到本次实际抓取的 Source。
- 搜索摘要、未抓取页面和没有证据关联的结论不能进入确定事实部分。
- 在固定真实问题上，来源可追溯率和 Claim 证据覆盖率达到本阶段设定的阈值。

### 本阶段明确不做

Evidence Store 先采用内存 Repository，不提前引入数据库、向量存储和长期 Memory。本阶段只建立可追溯数据链，不把启发式规则包装成完整 Verifier。

## 7. 阶段 5：Verifier

### 本阶段为什么现在做

Evidence Store 解决了“证据在哪里”，但尚未判断证据是否真的支持结论、是否存在冲突、是否过时。数据关系稳定后再实现 Verifier，评估结果才具有可解释输入。

### 本阶段交付与门禁

- 检查 Citation Coverage、Citation Correctness、文本蕴含、来源冲突、来源质量与时效性。
- Verifier 输出结构化判定、理由和待修复项，不直接覆盖原始证据。
- 未验证、冲突未解决或过期的 Claim 不能作为确定事实发布。
- 在人工标注的小型数据集上报告准确率、一致性和典型误判，并保留抽查记录。
- 关闭 Verifier 的消融实验能展示它对引用正确性和报告可靠性的真实影响。

### 本阶段明确不做

不引入长期 Memory、数据库持久化或产品界面；不让 Verifier 承担查询规划、网页抓取和报告写作职责。

## 8. 阶段 6：Memory

### 本阶段为什么现在做

只有 Claim、Evidence、Source 和验证状态稳定后，历史信息才具备可复用价值。过早保存对话全文会把噪声、旧结论和未经验证内容变成长期负担，因此 Memory 在证据和验证机制之后引入。

### 本阶段交付与门禁

- 会话记忆保存当前研究上下文，研究记忆复用已验证 Claim 与 Evidence，用户偏好记录输出风格和关注方向。
- Memory 条目携带来源、验证状态、更新时间、适用范围和失效策略。
- 时间敏感 Evidence 在复用前必须重新验证；偏好不能改变安全边界和证据发布规则。
- 同一主题的首次研究与更新研究能够展示新增、变化、失效和保持不变的结论。
- 对比无 Memory 基线，报告质量不下降，并量化重复搜索、时延和成本变化。

### 本阶段明确不做

不把模型私有思维链保存为 Memory，不无条件复用旧网页内容，不在本阶段同时引入完整 Web 产品和大规模评测平台。

## 9. 阶段 7：Deep Research 强化

### 本阶段为什么现在做

基础编排、证据、验证和记忆已经可用后，才能用可量化的反馈优化研究策略。本阶段关注 Agent 如何拆查询、何时并行、何时补搜、何时停止，以及如何在质量、成本和时延之间做预算决策。

### 本阶段交付与门禁

- 查询改写、候选来源多样化、最多有限轮次的补充搜索。
- 基于覆盖缺口、证据冲突、新增 Evidence 和剩余预算的停止条件。
- 有界并发 Researcher、故障隔离和网页、Token、费用、时间预算。
- 在固定问题集上，对比基础流程与强化流程的覆盖率、引用正确性、时延、成本和成功率。
- 达到预算时能生成明确的部分报告，不无限循环，也不伪造缺失信息。

### 本阶段明确不做

不把更长运行时间当作质量提升，不允许无界 Multi-Agent 扩张，不在指标稳定前建设复杂 Web UI。LangGraph 仅在状态图、并发和恢复需求已经明确时引入，而不是阶段 1 的依赖。

## 10. 阶段 8：产品化

### 本阶段为什么现在做

核心研究质量和运行边界稳定后，再把系统包装成可使用、可观察、可恢复的应用，避免 UI 掩盖算法和证据问题。该阶段把已有能力变成可演示的 AI 原生产品。

### 本阶段交付与门禁

- FastAPI 提供任务创建、查询、取消和结果接口，SSE 推送安全运行事件。
- Web UI 展示任务状态、研究计划、来源、证据、Verifier 结果和最终报告。
- 持久化运行、Checkpoint 和恢复语义明确；重启后不重复已经完成并计费的工具调用。
- 日志、指标和追踪覆盖模型、搜索、抓取、验证、成本、时延与错误类型，且不泄漏凭据或私有思维链。
- 通过端到端验收、取消/恢复测试、部署验证和最小安全检查。

### 本阶段明确不做

不为了界面效果改写已通过验证的证据规则，不把人工未审核的实验指标包装为生产承诺，不在产品代码中复制外部开源项目的核心实现。

## 11. 阶段 9：系统评测与开源对比

### 本阶段为什么现在做

只有完整系统及其可观测数据稳定后，质量、成本和时延对比才有意义。本阶段用固定数据集、消融实验、内部 Baseline 和外部开源基线验证每个关键设计的真实贡献，并沉淀论文复现与 Agent 评估能力。

### 本阶段交付与门禁

- 固定版本的中文评测集、数据集哈希、运行配置哈希和原始结果归档。
- 内部 Baseline 与消融：直接回答、单 Researcher、无 Verifier、固定轮次、完整版、Memory 首次研究与更新研究。
- 质量指标包括报告质量、Citation Validity、引用正确性、引用覆盖率、Research Coverage、Source Quality、Conflict Handling 和 Freshness。
- 工程指标包括成功率、端到端时延、Token 与费用、搜索/抓取/模型调用次数、重复网页比例、每条有效 Evidence 成本和失败恢复情况。
- LLM Judge 与人工抽查结合；同时展示质量和成本，不用单一综合分数掩盖差异。
- 评测可从固定配置复现，失败与不可用情况有明确记录。

### 与开源项目的对比要求

首批外部基线至少包括 [Open Deep Research](https://github.com/langchain-ai/open_deep_research) 和 [GPT Researcher](https://github.com/assafelovic/gpt-researcher)。二者只用于可复现对比和设计参考，不成为 DeepTrace 的核心代码来源。

对每个外部项目必须：

1. 固定具体 Git commit SHA，同时记录许可证、安装步骤、配置文件和运行命令。
2. 统一问题集与数据集版本，统一运行时间窗口，并尽可能使用相同模型或同等级模型。
3. 统一搜索预算、结果数量、网页预算、最大运行时间和成本统计口径。
4. 保存模型、搜索 Provider、配置哈希、原始报告、引用、Token、费用、时延和错误原因。
5. 报告报告质量、引用正确性、引用覆盖率、研究覆盖率、时延、成本和成功率；外部项目不可用时标记为 `unavailable`，不能计为零分。
6. 明确标注无法完全公平对齐的指标和原因，例如框架内置搜索器不同、模型不兼容、隐藏 Prompt、并发策略、缓存命中、引用格式或成本信息不可得。不能用“完全公平”描述存在差异的实验。

外部项目先运行开发集；环境与费用稳定后再决定是否运行隐藏集。DeepTrace 不复制这些项目的核心图、Prompt、Verifier 或停止策略。

### 本阶段明确不做

不只挑选对 DeepTrace 有利的问题，不更改外部项目结果来适配本项目格式，不把 `unavailable` 当作失败分数，不用未经复现的 README 宣称替代真实运行。

## 12. 全局阶段门禁

每次进入下一阶段前都必须满足以下规则：

1. 当前阶段自动化测试全部通过，且上一阶段已通过行为没有回退。
2. 当前阶段的真实验收问题可完成；外部网站限制导致失败时，必须记录可解释原因和系统行为。
3. 学习者能够解释新引入的模型、接口、消息或状态，以及它解决了上一阶段的什么真实问题。
4. 正式项目由学习者按文档手动更新；参考实现保持隔离并可独立运行。
5. 没有用后续框架、Fake/Mock、静态演示结果或手工篡改输出绕过当前问题。
6. Git 提交不包含真实 API Key、Cookie、Token、完整敏感请求头或未经说明的占位实现。
7. 本阶段的指标、失败记录和已知限制已写入验收记录。

如果任一项未通过，就停留在当前阶段修复，不提前创建下一阶段目录或代码。

## 13. 简历与面试叙事

这条路线最终形成的价值不只是“调用了大模型 API”，而是一条可验证的系统演进证据：

- 阶段 1 到 3 展示 Tool Calling、Agent loop、规划执行和工程模块化能力。
- 阶段 4 到 6 展示 RAG 数据建模、证据可追溯、Agent 评估、可靠性和 Memory 机制。
- 阶段 7 展示 Deep Research 策略、并发、预算和停止条件设计。
- 阶段 8 展示 API、Web UI、任务状态、恢复与可观测性的产品落地能力。
- 阶段 9 展示固定基线、消融、开源项目复现、质量/成本权衡和评估体系建设能力。

面试演示应从阶段 1 的最小闭环开始，解释每次演进由什么真实问题触发，再用证据链、评测结果和失败案例证明设计选择，而不是只展示最终页面。

## 14. 当前下一步

当前只实施阶段 1。先生成阶段 1 的手动搭建文档与隔离参考实现，再由学习者在正式项目中从空目录手动复现、运行真实测试并完成两道验收题。阶段 1 门禁未通过前，不开始阶段 2 的详细设计或代码实现。
