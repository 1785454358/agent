# 开源深度研究项目对比面试问答

本文回答面试官最可能从"市面上有类似项目"切入的追问。所有回答以当前源码和离线测试为事实边界；真实 Provider、benchmark 分数和在线评测不作为已完成事实陈述。

## 总体应答框架

不管被问到哪个项目，先给定位，再分维度：

> 开源深度研究项目大致分三类：**模型训练派**（通义 DeepResearch、OpenResearcher，核心资产是权重和合成数据）、**框架模板派**（LangChain open_deep_research、gpt-researcher，核心是易用和可配置）、**极简参考派**（dzhng/deep-research，核心是教学）。
>
> 我不追求把模型调得更聪明，而是研究"开放式 Agent 循环如何可控、可恢复、可审计"。所以差异不在研究质量，而在运行时治理。

## 对比速览

| 项目 | 类型 | 研究循环 | 运行时治理 |
| --- | --- | --- | --- |
| 通义 DeepResearch | 模型训练派 | 原生 ReAct + 未开源的 Heavy Mode | 容器侧几乎没有，重试为简单退避 |
| OpenResearcher | 模型训练派 | 长轨迹蒸馏 | 无 |
| LangChain open_deep_research | 框架模板派 | Supervisor + research 子代理 | 模型/搜索可插拔，无预算/账本 |
| gpt-researcher | 框架模板派 | 固定 pipeline | 插件式，无运行时约束 |
| HF smolagents | 框架模板派 | CodeAgent 写代码调工具 | 沙箱执行 |
| dzhng/deep-research | 极简参考派 | 单循环递归深入 | 无 |
| 本项目 | 工程 Harness | 三策略共享受控 Agent Loop | ModelGateway、ToolGateway、Ledger、Checkpoint、AgentOutcome |

## A. 定位与选型

### Q1：开源项目这么多，为什么还要自己写？和它们有什么区别？

因为目标不同。gpt-researcher 是固定 pipeline（planner → 并行 execution agent → publisher），追求开箱即用；LangChain open_deep_research 是 LangGraph supervisor，追求模型/搜索可插拔；通义是训练一个 30B 模型，追求 benchmark 分数。它们的共同假设是：外部调用基本可靠、进程不会崩、循环不会失控。

我的项目反过来把"失控"当作第一问题：所有模型调用经过 ModelGateway，外部工具经过 ToolGateway，每次受控退出产生结构化 AgentOutcome，崩溃后靠 Checkpoint + Ledger 恢复。区别不是谁的搜索更多，而是失败、恢复、审计方式是否明确。

### Q2：你了解 LangChain open_deep_research 吗？它和你最像。

像在都用 LangGraph、都做多角色。两点关键不同：

1. 它持续简化架构并用 benchmark 公开对比，把旧版 plan-and-execute / multi-agent 放进 `src/legacy/`，用实验证明当前设计更优。我保留三种可路由策略，因此欠一个"多策略到底值多少"的 A/B 证据，这是计划补齐的部分。
2. 它的治理边界更薄：模型角色可换、搜索可插 MCP，但没有工具预算、幂等账本和证据库这套运行时约束。

它对我是最直接的对标，也是最该借鉴的实验方法。

### Q3：通义 DeepResearch 开源了，为什么不直接用？

它是模型能力，不是我要解决的工程问题。它开源的是权重、约 200 行的 ReAct 推理脚本和数据合成代码。能力来自 CPT → SFT → GRPO 训练；容器侧没有 checkpoint、ledger、预算和证据库，Heavy Mode（IterResearch）也未开源。

我能直接借鉴的是它的方法论（IterResearch 上下文重构、Research-Synthesis 并行），但它的运行时不解决我的可靠性目标。

## B. 架构对比

### Q4：你的三种策略和 LangChain supervisor 多智能体有什么区别？

关键区别是"策略"和"循环"分离。LangChain 的 supervisor 与子代理是同一个 Graph 里的节点；我是三层：Session Graph 管会话，策略 Graph 管拆解协调，Shared Agent Loop 管模型—工具循环。

三个策略只在"怎么拆任务"上不同：

- Workflow：固定阶段、无依赖分支并行；
- Plan-and-Execute：`plan → select → execute → evaluate → 有界 replan`；
- Multi-Agent：`supervisor → Send 并行 researcher → aggregate → evaluate → 有界 follow_up`。

搜索、抓取、上下文裁剪、错误治理和退出共享同一个 Loop，因此修一处不会漏另外两处。

### Q5：上下文管理和它们有什么不同？

多数项目是"塞满就截断或摘要"。通义 Heavy Mode 的 IterResearch 更主动：每轮只用上一轮最关键的输出重建精简工作区，并维护持续演化的中心报告，缓解长任务的认知窒息。

我现在是双层：单次研究内，Context Policy 按完整工具交换成组裁剪，固定保留 system instruction、原始任务和当前约束，ModelGateway 在调用前二次校验这三个不变量；跨会话用滑动窗口加结构化摘要，摘要失败也走确定性裁剪兜底。

坦白说，IterResearch 的主动重建强于我的被动裁剪，这是下一步想吸收的能力。

### Q6：gpt-researcher 直接调 Tavily，你为什么加一层 ToolGateway？是不是过度设计？

取决于目标。只生成报告时直接调没问题；但我要的是工具调用可白名单、可限额、可去重、可证据化、崩溃后可重放，这些直接调都做不到。

ToolGateway 一次执行内完成：调用者与工具白名单、参数与 URL/SSRF 校验、Run/Mode/Agent 三级预算预留-提交-释放、缓存与 Singleflight、执行账本 claim（REPLAY / FOLLOWER）、证据落库，并且不重复执行已提交的副作用。

注意边界：`write_todos` 不经过 ToolGateway，因为它只修改可恢复状态，没有外部副作用。

### Q7：smolagents 证明"写代码调工具"比 JSON tool-call 高约 22 分，你为什么还走 JSON？

这正说明结构比模型更重要（它们 GAIA 上 code-acting 55% 对 JSON 约 33%，固定模型只换结构）。我选 JSON tool-call 是为了与治理目标兼容：schema 可校验、参数可白名单、调用可稳定 ID 化、可幂等重放。code-acting 需要沙箱执行任意代码，会绕过我的证据、预算和审计边界。

但这提醒我：JSON 路线在复杂任务上可能确实吃亏，这应该用实验验证，而不是嘴上辩护。

## C. 技术追因

### Q8：为什么三个策略共享一个 Agent Loop，不各写一套？

三种策略的差别只是任务拆解和协调，不是搜索、抓取、裁剪和错误处理。共享 Loop 让它们天然遵守同一套不变量：模型信封、工具权限、预算、tool call / ToolMessage 配对、恢复和 Outcome 契约，避免修一套漏两套，也避免策略私有状态污染全局 State。

### Q9：你的 retry 分层是不是想多了？

简单重试在 demo 里够用，问题在于失败归属不清会导致调用放大。我把 retry 分三类，各有唯一所有者：

- transport retry 属于 Gateway，只处理超时、限流和临时服务错误，不修正语义；
- semantic repair 属于 Agent Loop，把结构化失败作为 ToolMessage 回灌，让模型换参数或来源，不重复已提交的副作用；
- recovery replay 属于 Checkpoint / Worker / Ledger，用于进程崩溃和 at-least-once 重放。

这样同一次失败不会被三层各重试一遍。

### Q10：开源项目大多没有 checkpoint/ledger，你做这个有必要吗？

取决于是否承诺"长任务 + 可恢复"。我的 Loop 每轮都会调用外部工具，进程崩溃后如果只恢复图状态，已成功的 Provider 调用会重放。因此 Checkpoint 只保存可序列化控制状态，Ledger 用稳定 call ID 记录已提交结果，恢复时优先重放。

口径要收住：我降低 at-least-once 下的重复影响，不承诺任意外部副作用 exactly-once。

### Q11：AgentOutcome 为什么不能只有一个 stop_reason？

停止原因只回答"为什么停"。上层还需要判断结果能否使用、有哪些证据、发生了什么错误、消耗多少步骤、计划完成多少、能否继续。因此 Outcome 同时包含 status（completed / partial / failed / cancelled）、summary、evidence_ids、errors、iterations、executed_steps、budget 快照、plan_total / plan_completed 和 unfinished_todos，让策略能合并部分成功、暴露缺口，而不是把失败伪装成完成。

## D. 批判与压力

### Q12：你的项目在研究质量上，凭什么比开源项目好？可能还不如它们。

在纯研究质量上，我大概率不如通义（它有专门 RL 训练的模型和合成数据），也可能不如简单 pipeline 的产出多样性。我从不把卖点放在研究质量上。我卖的是可控（预算、权限、熔断）、可恢复（Checkpoint / Ledger）、可审计（Outcome / Evidence / 事件流），以及三策略共享一套治理、可做 A/B。质量我依赖外部模型，贡献是让它跑得住、说得清。

### Q13：这会不会是过度工程？去掉 LangGraph 还剩什么？

反过来问更准：去掉 LangGraph，这套仍可换别的方式实现，因为价值不在图引擎，而在运行协议和治理规则。是否过度取决于承诺：只做一次问答式调研，确实用不上 Ledger 和预算；但只要要求长任务、可取消、可恢复、可审计、多策略，这些就不是装饰。我承认部分治理（完整 Prompt Injection 检测、精确 Token 计量、在线 Eval）尚未完成，只到演进方向。

### Q14：你怎么评估自己？人家有 HLE / BrowseComp / GAIA，你有 benchmark 吗？

这是目前最弱的一环。我有 464 个离线测试，覆盖模型信封、tool call 配对、Gateway 边界、AgentOutcome、Checkpoint 恢复等运行不变量，但那是正确性测试，不是研究质量评估。系统化在线 Agent Eval 仍是演进方向。

一个已有起点是 `tests/integration/test_mode_evaluation.py`：它在脚本化数据集上对三种策略做确定性质量 / 成本 / 延迟代理对比。我会在此基础上分两步补齐：先建离线模拟环境（参考通义用离线语料加工具沙箱，不依赖 live API），再做同任务多策略 A/B 加 LLM-as-judge 多维评分。具体方案见[最小评测方案](../evaluation/agent-benchmark-plan.md)。

### Q15：你觉得哪个开源项目做得最好？你借鉴了谁？

分开看。工程上 LangChain open_deep_research 最值得学，因为它敢简化并用 benchmark 证明，还把旧架构留在 `legacy/` 供对照。方法上通义的 IterResearch 和 Research-Synthesis 最有启发：前者是主动重建上下文，后者是并行研究者加汇总 agent，正好对应我 Multi-Agent 的聚合层。实验精神上 HF smolagents 用"固定模型只换结构"证明代码调工具更优，这个对照实验方法值得学。

## E. 开放与演进

### Q16：如果吸收一个项目的能力，你先做哪个？

优先 IterResearch 式的上下文管理。它直接提升长任务质量且不需要重训模型，和我现有的摘要 / 裁剪机制处于同一位置，是最低风险、最高收益的升级。其次是离线模拟评测环境，用来补齐系统化评估的短板。模型训练这条路不会碰，那是完全不同的投入。

### Q17：跑一个真实复杂问题，你和通义会有哪些行为差异？

通义大概率研究质量更高（模型更强、搜索策略更成熟），但它更粗放，可能跑到超时才停，失败时缺少部分结果。我的差异在过程：有预算和熔断，有结构化失败回灌，有可引用证据，中断可恢复，退出会说明计划完成到哪、缺口在哪。它强在答案，我强在过程。

## 事实边界

- 可以说"实现了工具白名单、URL/SSRF 校验与信封隔离"，不要说"已完整解决 Prompt Injection"。
- 可以说"Ledger 降低 at-least-once 下的重复影响"，不要承诺任意副作用 exactly-once。
- 可以说"已有脚本化数据集上的确定性质量/成本代理对比"，不要说"已通过系统化在线研究质量评测"。
- 可以说"AgentOutcome 提供调用与步骤预算快照"，不要把估算写成 Provider 精确 Token 账单。
- 涉及通义、OpenResearcher、smolagents 等的 benchmark 数字时，注明为对方公开报告的结果，不作为本项目结论。
