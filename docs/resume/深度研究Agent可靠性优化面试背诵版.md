# 深度研究 Agent：可靠性优化面试背诵版

这份材料按成熟工程方案组织，适合学习、背诵和回答设计追问，不要求逐函数复述当前项目。设计选择可以用“我的设计是……”表达；上线规模、实际收益和已完成能力必须以[实测与事实边界](深度研究Agent最终实测与面试事实边界.md)为准。不要把参考方案说成亲自上线的经历。

## 先背这五句话

1. 我的重点不是多造几个 Agent，而是让搜索、阅读、证据交接、补查和回答形成可靠闭环。
2. 搜到了不等于抓到了，抓到了不等于读对了，读对了不等于最后答案完整。
3. 程序校验权限、身份、坐标和预算；模型判断语义支持、冲突和答案缺口，两者不能互相替代。
4. 优化先减少重复和无效工作，不先削掉关键证据；质量门槛不满足的省时方案不能上线。
5. completed、答案质量、来源约束和成本分开评估，单题高分不代表生产可靠。

## 一、项目介绍

### 30 秒版本

我做的是一个深度研究 Agent，主模式是 Plan-and-Execute：先拆成少量答案要点，再实时搜索和抓取原文，检查证据是否足够，不够就定向补查，最后生成带引用的回答。我重点研究的是 Harness 的可靠性：让原文从研究到评估再到写作不丢失条件和例外，并把来源版本、完成状态、时间、token 和搜索开销纳入统一验收。三种模式共享底层能力，不各自维护一套工具和证据逻辑。

### 2 分钟版本

这个项目面向需要查资料、比较多个概念、解释条件和例外的研究任务。直接让模型搜索后写答案有几个问题：可能根据摘要作答，可能抓到正文却读到不相关段落，也可能引用了错误版本的官方文档。

我的设计分为三层。编排层决定研究任务怎么拆、是否并行、何时补查；研究运行层统一管理工具权限、重试、预算和状态；证据层负责正文存储、结构化选段、实际可见引用与答案支持。Writer 不重新自由发挥，而是基于合格来源和已验证证据回答。

任务开始时固定答案要点和用户约束。研究员只负责自己的部分。评估阶段分别检查来源适用性与事实覆盖：来源是不是用户要求的官方资料和版本，原文是否真的支持结论、包含必要条件。只补缺口，不重复整项研究。每一阶段都保留可追踪的输入、输出和实际使用的原文位置。

评测也分层：离线回归验证边界和恢复，真实联网测用户看到的最终答案，模型评分衡量事实完整性与忠实度，程序规则核验来源和引用。优化时保持评分口径和预算一致，把质量与成本一起看。对我来说，最有价值的工程点是把“看起来会搜索”变成“能定位失败、能验证证据、能诚实收尾”的系统。

追问“效果提升多少”时，不背泛化百分比，直接给事实文件中的实际运行条件与结果。

## 二、最重要的面试问题：市场上已有 DeepResearch，为什么还做？

### 可直接背诵

我不会把“能联网搜索”或“有多 Agent”当成独创。这些已经有成熟实现。我做这个项目的目标，是把深度研究能力做成可控制、可验证的工程系统，并理解其中的关键设计。

差异主要在设计取向：第一，约束明确，指定资料和版本不能只停留在提示词里；第二，证据可追踪，能知道某个结论用了哪段实际可见原文；第三，过程可诊断，区分搜索失败、正文提取失败、选段丢失和写作遗漏；第四，评测可复现，把真实联网质量、来源正确性和搜索成本一起记录。

这些能力不是成熟产品没有，而是我选择重点落地和验证的工程问题。相比宣称全面超过现成产品，我更愿意说明自己的取舍、失败案例和验证证据。

### 追问：所以只是套 LangGraph？

LangGraph 提供编排和状态机制，但不会替我决定如何定义完成、如何筛选有效来源、如何保留原文条件、如何校验引用，以及怎么公平比较成本。框架解决执行骨架；项目工作在任务契约、工具边界、证据交接和评测闭环。是否有价值，要看这些逻辑有没有具体测试和运行证据，不能看画了多少架构框。

### 追问：为什么不直接用 GPT Researcher？

能满足需求时，直接使用成熟项目是合理选择。我会先看它的取材、压缩和研究交接是否符合场景，再决定复用还是自建。自建的理由应是约束、接入、可观测性或实验需求，不是为了重复开发。GPT Researcher 的上下文压缩实现可以作为理解取材路径的参考，不意味着必须引入它的全部依赖。[实现参考](https://github.com/assafelovic/gpt-researcher/blob/master/gpt_researcher/context/compression.py)

## 三、怎么把架构设计得标准，但不复杂？

### 可直接背诵

我会保留一个清晰的循环：规划、研究、评估、有限补查、写作。底层只保留几个共享能力：模型网关、工具网关、证据存储、状态与检查点、评测记录。不同运行模式主要改变调度，不复制工具、记忆和引用逻辑。

简单任务一个研究分支就够，只有问题能独立拆分时才并行。评估不额外堆多个“反思 Agent”，而是在现有判断里明确输出缺口和来源适用性。能够用确定性程序检查的内容，就不再让模型反复判断。

### 最小职责表

| 部件 | 只负责什么 | 不负责什么 |
| --- | --- | --- |
| Planner | 答案要点、少量互补查询、分支目标 | 改工具权限、改评分标准 |
| Researcher | 搜索、抓取、阅读目标原文 | 用摘要冒充正文、宣布全局完成 |
| Evidence layer | 原文、身份、可见范围与引用定位 | 用词面命中证明事实正确 |
| Evaluator | 来源适用性、语义支持、需求缺口 | 替失败步骤伪造进度 |
| Writer | 用合格证据完整回答 | 引入未批准来源、用常识补缺口 |
| Runtime | 预算、重试、取消、检查点与追踪 | 承诺所有网络请求必定成功 |

这是一份职责划分，不要求做成六个服务；模块边界清晰即可。

## 四、Plan-and-Execute、Workflow、Multi-agent 有什么不同？

Workflow 是相对固定的流程，适合路径清晰的任务。Plan-and-Execute 先形成任务计划，执行后根据明确缺口调整，适合需要逐步研究的问题。Multi-agent 适合多个独立方向并行，不适合把同一问题重复派给多个角色。

它们应该共享研究循环和证据规则，否则模式比较会混入不同检索质量。我的主模式选择 Plan-and-Execute，是因为计划与补查路径比较容易解释和追踪；不是因为它天然比另外两种更准确。

追问“多 Agent 一定更好吗”：不一定。并行能降低部分墙钟时间，但也增加重复搜索、token 和协调成本。Anthropic 的公开工程文章讨论了并行研究与信息交接，也强调评测；它的内部效果不能直接推导为我们的收益。[工程参考](https://www.anthropic.com/engineering/multi-agent-research-system)

## 五、网页已经抓到了，为什么还会读偏？

### 可直接背诵

抓取解决的是“拿到正文”，取材解决的是“让当前阶段看到正确的部分”。长文里可能包含多个 API、示例和版本说明，按通用关键词累计排序，往往会选到词多的泛化段落，而不是含条件和否定的关键段。

还有一个更隐蔽的问题：研究员已经读对，但评估时重新选段，用另一套排序把它丢掉，随后误判证据不足，触发重复搜索。因此我会检查整条交接链，不只检查抓取成功率。

### 追问：提示词写清楚不就行了？

提示词只能影响模型选择工具，不能保证后面的程序保留原文。权限、坐标、预算和可见引用需要程序落实；完整性与语义支持再由模型判断。比如必须知道“实际给评估展示了什么”，而不是只记录“数据库有这篇文档”。

### 追问：你怎么定位？

按步骤对齐轨迹：搜索返回哪些 URL，抓取存了什么，阅读展示哪些范围，评估最终收到哪些片段，Writer 又用了什么。针对同一份正文和相同预算做本地回放。如果研究读到了某段，评估输入却没有，就优先修交接与预算选择，不加研究轮数。

## 六、长网页如何选段？一定要向量库吗？

不一定。短文能放入预算，就完整读取。技术文档优先保留标题、段落、列表与代码结构，再按完整标识符和所属章节取材，并给多个答案要点分配空间。关键条件、否定和例外要和结论一起保留。

已读范围超预算时，阅读和评估共用规则，不各自维护相似的排序器。引用坐标始终指向原始正文，不对拼接摘要生成假坐标。整个阅读组放不下时明确报告省略，而不是截掉后半句。

向量检索适合更大资料集合和语义召回；精确版本、代码标识符和否定条件仍需额外处理。我会先用最简单可验证的方案，再依据失败分布决定是否增加 BM25、向量或 reranker，而不是默认把所有组件装上。

追问“find 和 query”：query 用于围绕问题选材，find 用于定位已经见过的原文术语；不要反复猜测翻译句子的原文。空命中或无新证据时必须改变动作。

## 七、证据交接该怎么设计？

### 可直接背诵

把原文证据与模型总结分开保存。原文是可回溯的事实基础，总结是便于下一阶段工作的压缩表示。交接至少包含结论、适用条件、来源身份和能回到原文的位置。压缩不能只保留结论而丢掉“通常、除非、不、特定版本”等限定。

原文到下一阶段存在两个门槛：先确认片段是当前合法可见材料，再确认它是否语义支持结论。匹配成功、引用编号合法，只证明定位正确，不证明结论正确。

Open Deep Research 的研究压缩和最终报告阶段是学习这一边界的参考：研究信息需要交给后续写作，来源也需要保留。本项目选择原文坐标与短引用，不照搬它的整套压缩流程。该仓库当前已归档，作为参考代码而非维护承诺。[研究实现](https://github.com/langchain-ai/open_deep_research/blob/main/src/open_deep_research/deep_researcher.py)、[提示设计](https://github.com/langchain-ai/open_deep_research/blob/main/src/open_deep_research/prompts.py)

## 八、“文档版本正确”和“证据 version 正确”是一回事吗？

不是。证据 version/hash 校验防止拿旧正文坐标引用新内容；产品或文档版本限制决定资料是否适用于用户问题。内部存储 version=1，并不代表文档就是用户指定的 v1。

我会分别检查实际抓取 URL、重定向后的 URL、文档标识和可见原文。页面的 canonical 链接可能指向最新版，不能用它替换实际版本身份。镜像文档也不能仅因为内容相似就当成官方资料。

来源适用性在现有评估调用中单列结果；程序只允许当前来源表中的编号，不合格或不确定的来源不能支持完成。模型仍可能误判版本，所以最终评测还需要独立来源核验，不能把“结构化输出”说成绝对正确。

## 九、如何保证回答有出处？

我会检查四层：来源能否使用、引用是否真的可见、原文位置是否一致、原文是否支持该结论。前面几层主要是程序规则，最后一层涉及语义判断。

Writer 只接收通过准入的来源和证据；被拒绝的资料不能从回退路径重新带回来。对于同一结论同时引用合格和不合格来源，我不会简单删掉不合格引用后仍保留原结论，而会重新核验或暂时拒绝该结论。

追问“能消灭幻觉吗”：不能绝对消灭。原文约束和引用校验减少可预防错误，语义误判和证据冲突仍需评测、审阅或明确不确定性。可靠性的目标是降低错误并能解释失败，而不是作百分之百保证。

## 十、证据不足怎么补查，怎么避免无限循环？

先把缺口映射到固定答案要点，再区分缺的是来源、片段还是理解。已有正文能回答时先补读；原始来源不适用时换正确来源；真正缺少资料才继续搜索。不要把全局问题再研究一遍。

停止依据是“完成需求”或“达到可解释的边界”：预算耗尽、无新证据、持续不可恢复错误。进度可以看新增来源内容、有效支持范围和需求覆盖，不看模型多写了几句总结。

分支结束和整个研究完成要区分。分支申请结束不等于全局需求 covered；有未完成待办或强退出原因也不能被兄弟分支的成功抹掉。失败时返回已有可信结论和具体缺口，不写一个看似完成的状态。

## 十一、不降质量，怎么省时间和 token？

### 可直接背诵

先减少重复：用少量互补查询覆盖多个相关要点，复用合法已抓取正文，避免补查再次研究整个问题。然后减少无效上下文：每轮只带必要指令、目标、近期完整工具交换和关键证据，不把完整历史反复发送。

对证据压缩，我优先去重复和无关内容，不删掉关键条件；对并行，只并行真正独立的任务。研究轮数是上限，不是必须用满。质量过关后，再用实际轮数分布调整上限。

最后做同口径比较：相同模型、任务、输出限制和预算，质量先过门槛，再比较时间、token 和搜索尝试。没有成功的质量配对，就不能宣称“质量不降、成本下降”。

### 追问：减少模型调用不就便宜了？

不完全。一次模型调用可能带很大的输入历史，少一次调用但每次更长未必省 token。搜索 API 通常另行计费；如果主要成本在搜索，应优先减少重复搜索，而不是只盯模型调用次数。

### 追问：缓存是否会导致旧资料？

需要区分运行内正文复用和跨运行缓存。运行内复用已有合法证据可以省调用；跨运行要根据资料时效性、版本和来源策略决定是否刷新。缓存命中不能替代当前任务的访问授权，也不能把历史摘要当作本次原文。

## 十二、怎么做一套成熟评测系统？

### 可直接背诵

我会做三类验证。离线测试验证协议、引用边界、预算和恢复；真实联网测试验证实际用户链路；故障注入测试验证超时、限流、抓取失败和恢复。冻结资料用于定位回归，真实联网是研究 Agent 的主要质量验收，两者不是互相替代。

数据按任务类型和难度分层，开发集用于调试，保留集用于验收；原始轨迹、配置身份、来源正文和评分结果都保存。金答案只能进入评分侧，不给研究模型提示。比较模式时统一模型和质量口径。

指标至少包括任务完成、事实正确性、忠实度、来源适用性、引用有效性，以及时间、token 和搜索成本。用成熟评分器，不把任意一个分数当全部验收。评分异常记 N/A，不能记零分，也不能一直重评直到满意。

这里的保留集、分层样本和故障覆盖是完整系统的设计要求；实际是否已满足、样本多少，应按事实文件回答。

## 十三、F1、Faithfulness、Goal 和 completed 分别是什么？

| 名称 | 回答什么问题 | 不能证明什么 |
| --- | --- | --- |
| Factual Correctness F1 | 最终回答与参考答案的事实覆盖是否兼顾遗漏和错误 | 不是关键词准确率，也不是整个系统成功率 |
| Faithfulness | 回答陈述能否被评分输入的上下文支持 | 上下文本身适用或真实，不能因此证明来源版本正确 |
| Goal | 判断实际结果是否达成参考目标；本轮评分输入仅是问题与最终答案 | 不是程序状态的同义词，也不是完整工具轨迹审计 |
| completed | 系统是否按自己的规则正常收尾 | 不是答案完全正确的认证 |

Ragas 的 FactualCorrectness 会拆分 response/reference 的陈述并判断事实重叠，可使用 precision、recall、F1；本项目 F1 不是 AnswerCorrectness 的事实/语义混合分数。[定义](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/factual_correctness/)

Faithfulness 看生成陈述与上下文的支持关系；若评分上下文遗漏 URL 等信息，相应陈述可能被判不支持。应审计输入与拆分结果，不能随意删除不利陈述或改评分结果。[定义](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/faithfulness/)

追问“高 Faithfulness 但低 F1”：可能只回答了少量正确事实，基本不乱说，但遗漏很多必要条件。追问“高 F1 但不完成”：可能主要事实正确，但来源限制、执行步骤或剩余需求未满足。两者都要回看轨迹，不直接加预算。

## 十四、怎么知道指标下降是真退化还是评分噪声？

先固定评分器、模型配置、数据和输出格式，保留原始 claim 拆分、蕴含判断及错误。检查下降对应哪些事实缺失，能否在实际回答和原文中找到证据；再看是否存在网页内容变化、评分输入丢失或拆分粒度变化。

LLM judge 不是完全确定的，temperature=0 也不保证每次一样。真正的比较需要预先设定重复次数、保留所有运行，并在足够样本上做配对统计和人工抽检，不能挑最好的一次。诊断题能证明某个失效链被修复，不能证明跨任务稳定提升。

## 十五、记忆模块怎么设计才标准？

### 可直接背诵

先区分三件事：当前研究的工作状态、跨会话用户记忆、可引用的来源证据。工作状态放检查点；长期偏好和经过准入的稳定事实放记忆存储；网页原文仍放证据存储。不要把“记忆”做成装下全部历史的一个大向量库。

读取时按用户/工作区命名空间隔离，带来源、时间、适用范围和过期状态。当前用户要求优先于历史偏好；涉及实时事实必须重新验证。写入时限制条数、去重和冲突处理，失败运行不直接写入未经验证的事实。

记忆生命周期要支持更正和遗忘，并评估跨任务收益与污染，而不是只测试“能存能取”。LangGraph 官方区分线程级 checkpointer 与跨线程 store，可以用来理解这两类状态的边界。[官方文档](https://docs.langchain.com/oss/python/langgraph/persistence)

## 十六、失败恢复是不是从 checkpoint 继续就行？

检查点保存的是已提交状态，不是保证外部请求恰好执行一次。如果外部请求成功后、状态提交前崩溃，恢复可能重复请求。需要用执行身份、幂等键、已完成结果或安全缓存处理这一窗口，并单独统计实际尝试。

我会区分暂态失败、输入/策略错误和取消：暂态连接问题有限重试；非法 URL 或参数不原样重试；取消向上传播。模型调用预算、供应商尝试和工具调用分别计量，重试不能逃过预算。

追问“恢复成功率多少”：必须有真实或故障注入数据才能给比例。检查点用例通过，只能说明该用例恢复行为正确。

## 十七、一个值得讲的优化案例

### STAR 版本

**背景：** 真实联网回答已覆盖很多事实，但仍触发补查，耗时和搜索上升。

**定位：** 对齐研究阅读和评估输入，发现研究已经读到关键条件，评估又用旧的通用词排序，挑了大的泛化窗口，丢掉了晚读的关键段。

**改动：** 阅读与评估共用结构选段，在实际已读范围内保留条件和例外；补上来源适用性及 Writer 准入，避免正确行为来自错误版本资料。

**验证：** 先写会失败的原文交接用例，再做完整离线回归和原预算三模式联网复测，保留源码、配置、轨迹和一次评分。最终结果只用事实文件的数据；未达到门槛就明确说未达到。

**反思：** 最大教训不是“提示词还不够强”，而是一个阶段局部正确不代表端到端正确。先定位证据在哪个边界丢失，修共享契约，比不断加研究轮数更有针对性。

## 十八、压力追问速答

**“这些不都是基础功能吗？”**

是基础能力，不应包装成算法创新。难点在这些边界一起成立：原文读对、跨阶段不丢、来源版本正确、预算不超、失败状态诚实，并用真实轨迹验证。我的价值是把基础能力做完整并能解释取舍。

**“为什么不换更强模型？”**

强模型值得比较，但程序把关键证据丢掉时，模型再强也可能只能猜。先修工程链路，再控制条件评估模型替换；不能把模型升级收益算作架构收益。

**“为什么不把全文都给模型？”**

短文可以。长文和多来源下，全文增加输入成本且可能淹没关键条件。我会保留必要原文组及定位，预算够时多保留，预算不够时显式记录缺口，不默默截断。

**“是不是一个 LLM 自己写、自己打分？”**

同模型 judge 有偏差，所以只能作为自动信号。来源和引用用程序校验，关键问题人工抽检；更强的证据来自保留集、足够样本和预登记比较，不是某个 judge 的一次高分。

**“你怎么保证完成？”**

我能保证完成标准和失败边界清楚，不能保证任意网络条件都成功。资料不足或预算耗尽时返回可信部分和缺口；不能为了成功率把失败改成 completed。

**“你实际负责什么？”**

按事实文件列具体模块、测试和真实轨迹。会讲完整理想架构，不等于所有部件都已上线；我会明确区分已实现和设计理解。

## 十九、三天背诵安排

- 第一天：背30秒介绍、成熟项目差异、六个职责与三种模式；每题能在一分钟内讲清。
- 第二天：背抓取/选段/交接、来源版本、补查和效率；能手画一条失败链并说出程序与模型的分工。
- 第三天：背四类指标、评测公平性、记忆与恢复、STAR 案例；用事实文件回答所有数字追问。

最终检查：不背没有证据的百分比，不把基础功能说成原创，不把检查点说成恰好执行一次，不把引用合法说成结论必然正确。
