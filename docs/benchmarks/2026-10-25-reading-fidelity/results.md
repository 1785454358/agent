# 为什么同样使用 Harness，回答质量仍然不稳定

日期：2026-10-25。本轮继续实现[上一轮未解决的取材问题](../2026-10-24-research-recovery/results.md)，保留了所有前后答案、失败样本和无效实验。

**已证实的问题是：原文提取和窗口选择会丢信息，来源和坐标校验不能证明结论正确，同模型复查也会放过错误。** “用了 Harness”只说明有运行治理和任务编排；选到了什么原文、哪些条件实际进入模型，以及模型怎样解释这些条件，仍直接决定结果。现有匿名竞品记录没有相同底座、相同资料和相同模式控制，不能把差距全部归因于某个框架，也不能据此断言是哪家模型更强。

## 本轮定位与实现

| 实际断点 | 修复 | 保留的边界 |
| --- | --- | --- |
| 主提取器认为长正文“可用”，却删掉 SQLite 页面的实质性列表；技术页的代码示例也可能整段丢失 | 使用保留更多原文的提取模式并纳入表格；只有明确 main/article 内的实质代码确实遗漏、结构化备用提取又保留了它时，才改用备用结果 | 不按正文更长就替换；导航代码不触发替换；HTTP、证据库、预览上限不变 |
| 中文需求直接对英文正文做字面匹配，读到泛泛主题词却错过具体机制 | 在原有来源选择调用中，额外返回按真实需求 ID 约束的原文语言读取查询；不增加翻译模型调用 | 最多六条、各 ID 一条，拒绝虚构/未分配 ID、空白、重复及超长查询；旧输出仍可用 |
| 工具读到了相关段落，父级又用中文重新排序而丢失它 | 将成功工具请求的 query 作为有界读取元数据随锚点保存，父级在同一预算内复用；新选择清除旧 checkpoint 的查询残留 | query 只作定位提示，不能变成引用或事实；来源、版本、hash 和坐标仍独立校验；旧锚点兼容 |
| 本轮初版按查询区分锚点，使同一范围重复占位 | 改回按来源/版本/hash/坐标去重；相同范围合并最多六条读取意图，兼容旧单 query 字段 | 64 个范围上限不变；容量诊断也按范围判断；不能让重复查询挤掉后面的独立材料 |
| 选中“因此……”短结论，却漏掉前段限制 | 将不超过既有块大小的相邻因果段落组合选取；预算放不下时整组省略 | 不跨实际可读范围，不自动补入未读文字；全部仍是原文坐标 |
| 长段的多个目标词被长度惩罚压过，短泛词段占用了每个需求的保留位置 | 独立焦点先比较匹配目标词数量，再用既有长度/稀有词排序；显式 API 目标规则继续保留 | 仍是有界词法定位，不能宣称已实现完整语义检索或保证覆盖 |
| 实际出现的规划/选来源连接失败直接导致取材降级 | Workflow 初始规划及候选选择对明确 transient 模型错误最多重试一次；第二次仍从外层共享预算调用 | SDK 仍每次派发一次传输；两次分别计数和记账；不重试 fatal、无效内容或预算拒绝，不扩大 20 次模型/100000 输入 token/240 次工具上限 |

实现集中于 `tools/scraper/*`、`tools/evidence_views.py`、`tools/evidence_units.py`、`harness/source_selection.py`、`harness/read_anchors.py`、`harness/model_recovery.py` 及 Workflow 规划入口。没有把 LangGraph/SQLite 的答案、专用网址或关键词写入生产逻辑，没有切换默认模型或思考模式。

[Trafilatura 官方说明](https://trafilatura.readthedocs.io/en/latest/corefunctions.html)区分了偏重精确和偏重召回的提取选项；本轮用实际保存的官方 HTML 做了提取对照，而非只修改配置后假定问题解决。

| 长读事务可能阻止 checkpoint 推进的相邻说明 | 不可见 | 可见 |

这证明了这一组真实材料的传递缺陷已经改善，不能推出所有新规划、新搜索和新来源都能稳定回答。重放摘要及哈希见 [runs.json](runs.json)，本地完整记录为 `.local-notes/reading-fidelity-2026-10-25/frozen-visibility.json`。

## 联网结果与尚未解决的问题

沿用完全相同的 LangGraph 主问题和 SQLite 对照问题，实际调用生产应用服务、搜索、抓取、证据库、模型和最终审查。使用新线程、local runtime、空 MySQL/Redis 配置及 lexical memory，与上一轮保持同样的服务隔离。模型配置仍为 `deepseek-v4.1-flash`、thinking disabled；预算上限不变。配置 ID 不等于供应商实际返回的模型版本，具体返回值逐次保存在记录中。

完整逐次指标见 [运行表](runs.md)，精确问题、来源、token、错误及原始文件哈希见 [runs.json](runs.json)。原始回答见 [outputs](outputs/)，没有人工润色、删除错误或用较好中间结果冒充最新结果。两道题均用于开发，不是留出集；计划和需求拆分随模型生成，自动覆盖数字不是独立正确率。

观察到的改善：一次中间 SQLite 输出已经补出了 rollback journal、长读事务和锁行为，使用 7 次模型、15 次工具；最终固定材料重放也保住了原先缺失的关键机制。不同阶段的 LangGraph 回答已能避免部分过强组合条件，某次也给出了恢复调用和节点重跑说明。

最后一次成对联网复测 `release-check` 两题均返回 `insufficient_evidence`：LangGraph 69.318 秒、10 次模型、43 次工具；SQLite 34.581 秒、9 次模型、25 次工具。随后发现并修复本轮引入的重复锚点容量问题，追加主问题 `capacity-check` 样本单独列入运行表。不能用中间某次更好的输出替代失败，也没有获得稳定的端到端质量提升证据。

去重后的主问题追加实测为 **44.027 秒、11 次模型、30 次工具、partial_reason 为空**。该原始回答重新覆盖 Store、`Command(resume=...)` 和 interrupt 节点重跑，也未再把 Store 与 checkpointer 的组合写成必须同时启用。它比上一轮 35.348 秒、7 次模型更贵，不能称作提速；仍只有一个追加样本。SQLite 未追加去重之后的联网采样，最近一次漏答继续作为未解决项保留。

仍存在以下问题：

- SQLite 最新运行仍是 `insufficient_evidence`。能找到更多官方锁/提交资料，也不等于每次都把长读事务机制带入并正确使用；部分新运行仍漏答。
- LangGraph 有运行再次漏掉 `Command(resume=...)` 与 interrupt 节点重跑，或将线程状态索引边界扩大成“不提供跨线程读取机制”。自动完成仍可能含有漏项或过强断言。
- 恢复语义容易混淆：故障后的成功 task 写入保留、super-step checkpoint 和 interrupt 所在节点重新执行是不同情形，不能以其中一条替代另一条。核对依据见[官方 interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)。
- SQLite 某些回答仍把旧的只读/`-shm` 限制写得过强，或把“checkpoint 能推进到读者需要的位置”简化成“只有所有读者结束才能推进”。列表恢复后，历史例外和限定同样需要正确理解；依据见[官方 WAL 文档](https://www.sqlite.org/wal.html)。
- 来源选择、读取与核验仍有模型判断；本轮修复不意味着全文都可见，也不意味着词法命中就是事实支持。响应会再次装配窗口，后续仍需检查从取材到最终写作的端到端可见性。
- 当前默认批量路径由宿主安排搜索、抓取和多次读取，核验发现缺口后主要重新规划补查查询。它没有在同一次核验中自由回到已保存原文逐段排查的工具闭环。因此“查到了页面”和“缺口已经有材料”之间仍可能断开；增加更多分支或自评调用不能自动修复这个断点。
- 实测保留了一个候选选择连接失败、两个初始规划连接失败的样本。连接失败会污染质量比较；它们仍列入运行表，并标明错误，未被隐藏。

## 撤下的审查实验

尝试在原有最终审查的一次调用内，为最多六个显式“必须/只有……才”等断言加入逐条 verdict 和逐字原文证据；宿主检查 ID 完整、引用真实可见、被否定原句是否改动。协议约束测试可通过，但实际质量未改善：

1. 冻结上一轮 LangGraph 原稿及当次写作可见原文，模型仍把 Store 与 checkpointer 的组合示例当成必要条件，返回 supported、issues 为空，正文不变。
2. 冻结本轮一次 SQLite 原稿及其实际可见原文，模型仍把 checkpoint 推进条件和 WAL 回卷条件混淆，返回 supported、issues 为空，正文不变。

这两次各只有一次模型调用，底座与模式不变。**结构化字段和逐字引用只能约束协议，不能保证引用蕴含结论。** 试验代码和原始调用已归档到本地 `rejected-claim-ledger/` 与 `frozen-review-*.json`；生产审查恢复为本轮修改前的版本，未保留无效提示或新增字段。摘要与哈希见 [runs.json](runs.json)。没有把这两次探针计入端到端运行的模型次数。

## 验证与后续判断

- 后端最终全量：**1542 passed, 2 deselected**，74.89 秒。排除项为 real 标记测试；真实调用由本报告的逐次记录覆盖。
- 独立评估环境：**66 passed**，19.92 秒；没有修改独立评估包。
- 新行为均先记录失败再实现，包含提取完整性、跨语言实际读取、需求范围拒绝、元数据不成为支持、旧状态清理、因果段整体预算、独立焦点和逐次计费的短暂失败恢复。修复了“读取元数据被整体复制成事实支持”的兼容问题，事实支持只取原文坐标与实际 quote。
- Scoped Ruff、已跟踪 diff 空白检查和新增文件空白检查通过；对照本轮修改前副本进行代码复核，检查来源授权、版本、预算、取消传播、序列化及旧协议。
- 中途一次 1535 项回归出现 5 条 aiosqlite 事件循环关闭后的线程警告；随后 1540 项及最终 1542 项这两次未出现。没有修改数据库代码，也不据此声称已经修复线程清理问题。
- 前两轮 benchmark 的文件清单逐项校验未变。新输出、运行摘要、日志与本轮代码前后哈希见 [manifest.json](manifest.json)。

继续提升质量的重点应转向：当核验发现缺口时允许有目标地回到原文检查上下文，减少多层重复截取；用固定原文和留出问题分开比较取材能力、模型判断及最终写作。不要以增加节点、加长提示词、提高自评覆盖率作为成功标准。当前实验也不足以确定替换成哪款底座会更好，需要同资料、同预算的对照才能判断。
