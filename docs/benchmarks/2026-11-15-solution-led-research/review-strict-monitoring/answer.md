## 一、选定方案与依据

- 监控能力：Uptime Kuma 按间隔检查 HTTP 等站点、记录响应时间、通过 90+ 通知提供方告警，数据存自有数据库 [4]。HTTP(s) 监控默认 2xx 成功，默认跟随最多 10 次重定向并评估最终状态码，可设置心跳间隔、重试、超时和接受状态码 [5]。
- 运行条件：官方 Docker 命令为 `docker run -d --restart=unless-stopped -p 3001:3001 -v uptime-kuma:/app/data --name uptime-kuma louislam/uptime-kuma:2`，要求 `/app/data` 所在文件系统支持 POSIX 文件锁，避免 NFS 类存储导致 SQLite 损坏，支持主流 Linux 发行版 [2]。
- 通知：Settings → Notifications → Add New Notification 选 SMTP，填主机名、端口（465/587）、加密方式、用户名密码、发件地址；Gmail 需开两步验证并生成 16 位应用专用密码，个人 Gmail 每日约 500 封上限，Workspace 约 2000 封 [3]。保存时有 Default Enabled 与 Apply on all existing monitors 选项，可把通知挂到全部监控项 [6]。
- 历史：监控、通知设置和运行历史全部存于 `/app/data` 的 SQLite 数据库，必须挂载持久卷，否则重部署丢数据 [4]。清理任务当前按全局保留期删除超过 30 天的旧数据；按监控项自定义保留时长是未实现特性，已关闭为“不计划” [1]。v2 改为只存聚合结果以提升性能，保留更多数据仍影响性能 [1]。

## 二、检查频率与容量

心跳间隔默认 60 秒，可低至 20 秒；更短间隔发现更快，但增加被监控服务负载和数据库行数，60 秒对多数服务是合理默认 [5][7]。本方案取 60 秒：20 站点约每分钟 20 次请求。20 站点在该配置下的具体资源占用未量化，属未核实项；建议部署后观察容器 CPU/内存与数据库增长。

## 三、通知渠道

主渠道 SMTP 邮件，发给团队 5 人。可在 To Email 填写团队邮件组地址；单个通知是否支持同时填写 5 个独立收件地址未核实，若界面仅支持一个地址，则需建邮件组或为每人建通知并挂到全部监控项 [6][3]。备选可加 Slack/Discord webhook，Uptime Kuma 支持 78+ 或 90+ 种通知 [4][7]，但本方案不依赖付费功能。邮件发送量估算：20 站点 × 每分钟 1 次检查，仅在状态变化时告警，正常远低于 Gmail 每日 500 封上限 [3]；若监控项频繁抖动，应调高重试次数而非换邮箱。

## 五、部署步骤

1. 确认服务器为受支持 Linux，安装 Docker Engine 与 Compose v2，验证 `docker --version`、`docker compose version` [8][2]。
2. 创建目录并固定镜像版本，数据目录放本地存储（勿用 NFS）[8][2]：`sudo install -d -o "$USER" -g "$USER" /opt/uptime-kuma && mkdir -p /opt/uptime-kuma/data`。
3. 启动容器：

```bash
docker run -d --restart=unless-stopped -p 3001:3001 \
  -v /opt/uptime-kuma/data:/app/data \
  --name uptime-kuma louislam/uptime-kuma:2
```

4. 浏览器访问 `http://服务器:3001`，立即创建管理员账号（未建账号前任何人可抢占实例）[4]。
5. Settings → Notifications 添加 SMTP，填服务器、端口、加密、账号、应用专用密码、收发件地址，点 Test 验证后 Save，勾选 Apply on all existing monitors [6][3]。
6. 逐个添加 20 个监控项：类型 HTTP(s)，URL 含 `https://`，心跳 60 秒，重试 1–2 次，超时 15–30 秒，接受状态码 200–299 [5]。
7. 验证：手动停一个站点或改错 URL，确认邮件到达；检查 `/app/data` 持久化，重启容器后历史仍在 [4]。
8. 历史保留：在 Settings 中核实是否存在全局保留期设置；本次材料未给出 UI 中 30 天保留期的具体配置项，若无可配置项则按默认清理行为运行，并标注为未核实 [1]。

## 六、一致性与缺口

- 步骤依赖齐全：Docker、端口 3001、持久卷、SMTP 凭据均覆盖 [8][2][3]。
- 费用与步骤一致：主线 0 元增量，未引入付费功能；可选域名/证书实价未核实 [8]。
- 缺口：30 天历史的具体配置入口与上限在可见材料中未确认，仅确认全局清理删除超过 30 天数据、按监控项保留期不计划支持 [1]。若团队要求“每站点独立 30 天”，当前主线不满足，需另行评估。
- 未核实项：20 站点单机资源占用、可选域名/证书实价、SMTP 服务商具体限额（除 Gmail 约 500 封/日外）、单通知多收件人支持 [3]。

## 七、取舍

选开源自托管而非托管服务：无按监控项费用、数据自持、可复用闲置服务器 [4][7]；代价是需自行维护 Docker、备份 `/app/data`（含通知凭据，按敏感数据对待）[8]，且 30 天保留只能依赖全局策略 [1]。若后续需要按站点差异化保留或更强 SLA，再评估托管服务，实价未核实。
