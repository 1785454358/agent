## 一、主线与核实情况

- **产品**：Uptime Kuma，开源、单容器 + SQLite，监控数据存自有数据库[1]。
- **HTTPS 监控**：Monitor Type 选 HTTP(s)，填含 `https://` 的完整 URL；默认 2xx 为成功，默认跟随最多 10 次重定向并评估最终状态码[2]。
- **检查频率**：心跳间隔默认 60 秒，可低至 20 秒；更短间隔增加被监控服务负载和数据库行数，60 秒对多数站点是合理默认[2][3]。20 项×60 秒约每分钟 20 次请求，单机容量属方向性判断，未量化核实[2][3]。
- **通知**：支持 90+ 通知渠道[1][4]；SMTP 在 Settings → Notifications → Add New Notification 配置，需主机名、端口（465/587）、加密方式、用户名密码、发件地址[5]。Gmail 需开两步验证并生成 16 位应用密码，个人 Gmail 每日约 500 封上限，Workspace 约 2000 封且部分域可能禁用应用密码[5]。
- **30 天历史**：数据全部存于 `/app/data`（SQLite），必须挂载持久卷，否则重部署即丢失[1][6]。清理任务按全局保留期删除旧数据；按监控项自定义保留时长是未实现特性，已关闭为“不计划”[7]。v2 只存聚合结果以提升性能[7]。**全局保留期的默认值及设置路径未在证据中确认，需部署后在设置中核实并设为 30 天。**
- **运行条件**：需支持 POSIX 文件锁的文件系统，避免 NFS，否则 SQLite 可能损坏[6]；支持主流 Linux 发行版[6]。

**明确假设**：①闲置服务器可装 Docker 并能出网访问 20 个目标站点；②团队已有可用 SMTP 邮箱（如 Gmail 应用密码）；③服务器电费与带宽视为已有成本，不计增量；④对外访问面板需域名与 80/443，若仅内网使用可省。

## 三、部署步骤（Docker 主线）

1. **验证环境**：`docker --version`、`docker compose version`；确认 `/opt` 为本地存储、非 NFS[8][6]。
2. **建目录**：`sudo install -d -o "$USER" -g "$USER" /opt/uptime-kuma && cd /opt/uptime-kuma && mkdir -p data backups`[8]。
3. **写 compose.yaml**：镜像固定 `louislam/uptime-kuma:2.5.8`（当前稳定 v2 版本，含管理员 RCE 修复）[8]；端口仅绑 `127.0.0.1:3001`，卷映射 `./data:/app/data`[8][6]。
4. **启动**：`docker compose pull && docker compose up -d`，`docker compose logs --tail=100` 确认无数据库/文件锁报错[8]。
5. **本地验证**：`curl -I http://127.0.0.1:3001` 返回 200/302 即正常[8]。
6. **建管理员账号**：浏览器打开面板立即创建，未建账号前任何人可抢占实例[1]。
7. **加 20 个监控**：逐个选 HTTP(s)、填 https URL、心跳 60 秒、重试 1–2 次、超时 15–30 秒、接受状态码 200–299[2][3]。
8. **配 SMTP 通知**：填主机/端口/加密/账号/发件地址，点 Test 收信后 Save；勾选“应用到所有现有监控”使 20 项全覆盖[4][5]。
9. **设 30 天保留**：在设置中确认全局历史保留期并设为 30 天；该默认值与路径未核实，需以实际界面为准[7]。
10. **验证**：手动停一个站点看是否收到邮件；确认数据目录有 SQLite 文件增长，30 天清理按全局保留期生效[7][1]。

## 四、一致性与缺口

- 20 项 × 60 秒 ≈ 每分钟 20 次请求，单机轻量可承受属方向性判断，具体容量未量化[2][3]。
- 30 天历史由全局清理实现，**不能按监控项单独设 30 天**；若需更长保留会影响性能[7]。全局保留期默认值与设置路径未核实。
- 公网面板的域名/证书实价**未核实**；若只用内网访问则无此项。
- 邮件日发送量取决于故障频率，正常远低于 Gmail 500 封/日上限[5]；若站点频繁抖动需调高重试次数。
- 服务器电费与带宽未计价，按已有沉没成本假设不计增量；若需计入，则总费用需另行核算。
