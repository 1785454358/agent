**结论：选 Uptime Kuma 开源自托管主线，部署在现有闲置 Linux 服务器上，用 Docker 运行，20 个 HTTPS 站点按 60 秒间隔检查，SMTP 邮件通知，30 天历史需在设置中核实全局保留期。增量现金支出按 0 元计，远低于 300 元上限；前提是服务器、电费、带宽和 SMTP 邮箱均为已有资源，且团队能通过本机或另行配置的安全通道访问面板。**

## 四、部署步骤

1. **验证环境**：确认 Linux 发行版受支持 [2]；安装 Docker Engine 与 Compose v2；确认可出网访问 20 个目标站点。
2. **建目录**：`sudo install -d -o "$USER" -g "$USER" /opt/uptime-kuma && cd /opt/uptime-kuma && mkdir -p data`。数据目录须在支持 POSIX 文件锁的本地存储上，勿用 NFS [2]。
3. **启动容器**（官方命令，端口仅绑本机更安全）：
```bash
docker run -d --restart=unless-stopped \
  -p 127.0.0.1:3001:3001 \
  -v /opt/uptime-kuma/data:/app/data \
  --name uptime-kuma louislam/uptime-kuma:2
```
4. **验证**：`curl -I http://127.0.0.1:3001` 应返回 200/302 等有效响应 [3]；`docker logs` 无数据库/文件锁报错。
5. **建管理员账号**：浏览器打开 `http://127.0.0.1:3001`，立即创建账号，避免被他人抢占 [1]。
6. **配 SMTP 通知**：Settings → Notifications → Add New Notification，选 SMTP，填主机、端口、加密、账号、发件地址，点 Test 确认收信后 Save [6][7]。勾选 Default Enabled 或 Apply on all existing monitors，使 20 个监控项都挂上通知 [6]。
7. **加 20 个监控项**：Add New Monitor，类型 HTTP(s)，填完整 `https://` URL，心跳间隔 60 秒，重试 1–2 次，超时 15–30 秒，接受状态码默认 200–299 [4]。
8. **确认 30 天历史**：检查全局保留期设置为 30 天（具体路径本次材料未给出，需在设置中核实）；确认 `/app/data` 已持久化，否则重部署丢历史 [1][2]。
9. **验证故障通知**：临时停一个站点或改错 URL，确认邮件在重试耗尽后到达。

## 五、一致性核对

- 20 个监控项与 60 秒频率：算术为每小时1200次、每天28800次，但单机容量未量化，需实测；不能判为已满足资源约束。
- 30 天历史：原文[8]提到夜间清理任务删除超过30天的数据，但全局保留期具体配置路径/默认值未给出，需部署后核实；非付费功能方向有依据，但配置方式未核实。
- SMTP 通知：覆盖全部监控项，无额外付费依赖（假设已有邮箱）；Gmail 需 2FA + 应用专用密码 [7]。
- 总费用：0 元增量现金支出，低于 300 元/月；若加域名/公网代理，实价未核实；服务器电费/带宽为未计入的已有沉没成本。
- 部署依赖：Docker、本地POSIX文件锁存储、SMTP凭据、本机访问或另行配置的安全通道；第二通知渠道如Slack/Discord需相应Webhook凭据 [5]。

**主要风险：** 服务器单点故障会导致监控本身不可用，建议至少保留外部人工巡检或第二通知渠道（如 Slack/Discord，Uptime Kuma 均支持 [5]），但需配置对应Webhook凭据。
