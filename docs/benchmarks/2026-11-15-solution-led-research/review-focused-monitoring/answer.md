**结论：主线选 Uptime Kuma 开源自托管，部署在现有闲置 Linux 服务器上，用 Docker 运行，监控 20 个 HTTPS 站点，默认每 60 秒检查一次，SMTP 邮件通知，目标保留 30 天历史。增量月费按 0 元计（服务器已有，电费/带宽视为沉没成本），但“30 天历史”的可配置性、20 站点单机容量与公网域名实价尚未完整确认，故不能据此承诺整个方案已完全核实且低于预算。**

## 主线与依据

- **HTTPS 监控**：Monitor Type 选 HTTP(s)，填含 `https://` 的完整 URL；默认 2xx 成功，默认跟随最多 10 次重定向并评估最终状态码，可设心跳间隔、重试、超时、接受状态码 [1]。
- **检查频率**：默认 60 秒 [1]；材料另提到每 20 秒检查的服务描述 [2]，但未给出可配置下限的官方说明，故本方案按 60 秒执行，不把 20 秒当作已核实下限。20 个站点每 60 秒约 28,800 次检查/天，单机可承受属**明确假设**，可见材料未给 20 站点的量化容量数据。
- **通知**：Settings → Notifications → Add New Notification 选 SMTP，填主机、端口、加密、用户名密码、发件地址；Gmail 需 2FA 后生成 16 位应用密码，个人 Gmail 每日约 500 封、Workspace 约 2,000 封上限 [3][4]。保存时勾选 Default Enabled 或 Apply on all existing monitors 可覆盖全部监控项 [3]。端口/加密按邮箱商实际：Gmail 可用 587/STARTTLS [3] 或 465/SSL [4]，二者并列，以实测为准。
- **历史**：全部数据存于 `/app/data` 的 SQLite，必须挂载本地持久目录，NFS 等文件锁不可靠会导致数据库损坏 [5][6]。按监控项自定义保留期是未实现且被关闭为“不计划”的特性请求；v2 只存聚合结果，保留更多数据仍影响性能 [7]。**30 天保留**：可见材料只以“夜间清理删除超过 30 天数据”的讨论形式出现 [7]，未给出可核对的设置项名称或默认值，属**未核实**，部署后需实测确认；若实测无此配置，需自行加定时清理脚本，这属建议而非原文功能。

## 部署步骤

1. 确认主机为常见 Linux 发行版，装 Docker Engine 与 Compose v2；`/app/data` 放本地磁盘，不用 NFS [6][8]。
2. 建目录并固定镜像版本：按 [8] 钉到 `louislam/uptime-kuma:2.5.8`（当前稳定 v2 并含管理员 RCE 修复）；生产建议钉到具体小版本 [6][8]。
3. 启动容器，端口仅绑 `127.0.0.1:3001`，由 Caddy 等反代对外提供 HTTPS [8]：

```bash
docker run -d --restart=unless-stopped \
  -p 127.0.0.1:3001:3001 \
  -v /opt/uptime-kuma/data:/app/data \
  --name uptime-kuma louislam/uptime-kuma:2.5.8
```

4. 浏览器打开面板，**立即**创建管理员账号，否则任何拿到 URL 的人可抢占实例 [5]。
5. 配 SMTP 通知并点 Test，确认收件后勾选应用到全部监控项 [3][4]。
6. 逐个添加 20 个 HTTP(s) 监控：完整 HTTPS URL、间隔 60 秒、重试 1–2 次、超时 15–30 秒、接受码 200–299 [1][2]。
7. 验证：手动停一个站点看是否收到邮件；查 `/app/data` 数据库增长与清理任务是否删除 30 天前数据。
