# 回答质量诊断与改造建议

日期：2026-11-19。范围：回看已保存的真实模型回答、覆盖判定、证据窗口和代码；调研外部一手资料。本轮没有改运行代码，没有重新调用项目模型，也没有把下面的预期当作实测收益。

## 结论

当前应优先修复“材料如何成为答案”的共用链路。三种模式都已取得同一份完整 RFC 9110（447,606 字符）和 RFC 6585（15,587 字符），但关键章节未稳定进入核验与写作视野；完成条件还混合事实查证、工程设计和否定约束；最终复核漏掉了正文与伪代码的实质矛盾。

本轮能确认这些具体失败，尚不能量化它们在所有问题中的占比，也不能排除模型能力、采样和提示词对结果的影响。不能据此宣布某模式总体质量最好。先修共用材料链路，再做模式与模型的受控比较。

## 已定位的问题

### 1. 长文定位没有保证关键章节到达核验器和写作者

三种模式都漏掉真正的 503 定义。Workflow 的写作片段包含 331570–331946，即 413 的临时情况条款，回答却将其中的 SHOULD 归到 503；实际 503 是 MAY。两者属于不同章节，不能仅凭共同出现 Retry-After 就互用。标准原文见 [RFC 9110 §15.5.14](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5.14) 与 [§15.6.4](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.6.4)。

Plan-and-Execute 的写作原文窗口只有约 167164–169343、174504–176164、203666–205534，因此无法直接依据 §9.2.2 和 §15.6.4，却在结论中把局部没有看到自动重试依据泛化为两规范均未给出通用许可。实际依据在 [§9.2.1–9.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)。

对应实现：`strategies/evaluation_materials.py` 的单来源 3000–6000 字符窗口、32 来源和 128 引用单元上限；`harness/batch_collection.py` 的有限阅读查询；`tools/evidence_views.py` 的词面窗口选择。限制本身有必要，问题是选择单位和覆盖优先级不可靠，不能简单取消上限。`support-first` 会优先延续已有支撑，错误的章节定位可能沿核验、写作继续传递。

**置信度：高。** 窗口遗漏和错误归属可直接复核；具体各排名权重贡献尚未做消融。不能断言这是上一轮节省 token 改动新引入的退化。

### 2. 需求契约把不同性质的问题混成“必须找到规范原文”

三个规划都把“缺失或无效 Retry-After 的处理规则”放进必须查到的 RFC 事实，且 `allow_unknown=false`。用户实际要求还包括自行提出策略、区分规范与建议；合理交付应明确哪些有规范依据、哪些是客户端建议，而不是默认每项设计都必须有直接规范条文。

Workflow r1 已含断连风险，r5 再次要求断连不确定性，形成重叠验收。其 r2 判定同时出现“没有强制处理规则/客户端自定”的已解释理由与缺失状态，说明缺口类型和交付完成状态尚未对齐。Multi-Agent r6 要调查 POST 去重承诺是否存在，最终却将“缺乏去重/幂等键保障承诺”列成未覆盖；“是否存在”的判断不能无意间变成必须找到一个承诺。

**置信度：高（契约与判定存在混用）；中（各项导致终止的独立贡献）。** 不应简单把所有 `allow_unknown` 改为 true，更不能把没查到自动记成已完成。需要分类处理并记录查证范围。

### 3. 补救动作没有对准“文档已在，但章节未读到”

`strategies/evidence_evaluation.py::supplement_plan` 中，只要 `assessment.recovery_tasks is not None`，便解析查询并提前返回；即使 `allow_reread=true`，也返回空 `reread_actions`。已有来源的 `build_source_outline` 位于此返回之后，因此这条建议路径绕过补读导航。

此外 `strategies/source_reread.py` 只纳入不超过 900 字符的块，再受每来源 32 块和调用方 24 条目录限制。它并非完整文档目录，长条款可能不能成为候选。

冻结资料下反复搜索相同 RFC 无法补上缺失章节；无新证据复用核验是合理行为，但无法修复读错位置。应调整恢复动作，而不是把复用关掉再全量核验。

**置信度：高（代码分支）；中（每轮效果）。** 当前事件不完整保存原始规划输出，不能把所有未完成都归因于该分支。

### 4. 最终复核没有按行为检查正文与代码

Plan-and-Execute 正文明确要求 POST 的 429/503 也必须经过防重复保护，但代码 `if resp is 429 or resp is 503` 直接等待并继续；`post_is_dedup_safe()` 只在断连分支出现。反例：POST、未承诺去重、首个响应 429、预算充足，代码会第二次发送，违反其自己的策略和本题约束。

同一轮复核的 c3 却为 passed，理由称 POST 仅满足安全条件才重试。说明“写了检查名并返回 passed”并不等于检查了实际控制流。当前 `responses/constraint_audit.py` 明确是窄范围防线，只识别特定风险开关/句子及 send 的预算参数，不能泛化为 POST 所有路径都安全。

Workflow 还有开头对 POST 可重试信号的含糊表述与后文严格条件不一致。两模式伪代码对网络异常的捕获也没有明确展开，宜在验收中按异常路径检查，但不能只凭伪代码简写断言真实运行必然报错。

**置信度：高（PE 反例、复核漏判）；中（简写代码的异常含义）。**

### 5. 覆盖判定、引用合法性和答案正确性需要分开度量

有效的来源编号、版本、哈希和字面引用，只能验证引用可追溯；不能单独验证命题是否被引用支持、章节适用条件是否正确、代码是否落实限制。已有 1857 项离线测试通过证明工程协议回归稳定，不证明这些实测回答已正确。

额外回看 Python 诊断样本 `.local-artifacts/frozen-efficiency-dependent-v7/plan_execute`，其 r4 取消清理缺口伴随 `read_anchor_omitted`；跨语言样本 `.local-artifacts/frozen-efficiency-parallel-v7/multi_agent` 的 Java 取消/限制 r5 也伴随该诊断。它们支持继续检查阅读覆盖，但尚未逐句建立这两题的标准答案，不能据此声称同一根因已被全部证明。

当前事件仅存复核问题数量与判断，缺少完整初稿、修订差异和逐项依据；因此不能准确区分哪些错误在初稿出现，哪些在修改时产生。

## 建议流程与实施顺序

### 第一批：先让研究拿到正确、完整的依据

1. **建立轻量回答契约。** 区分事实查证、设计/比较交付、必须遵守的约束；每项关联用户原句，合并重叠事实。否定约束作为验收规则；规范未规定的策略明确作为建议，不制造必须找到原文的要求。不要增加一个独立“契约审核模型”，先改现有规划输出和宿主校验。
2. **建立章节索引与保留上下文的阅读单元。** 存正文坐标、标题层级、版本、章节锚点、必要前提和例外；检索先匹配明确章节/术语，再读完整相关单元。标题属于定位信息，命题仍必须由正文支撑。HTML、纯文本、PDF 各用适配器，无法可靠解析时显式退回普通定位。不能给任意原文硬套 RFC 专用解析。
3. **补读优先的缺口恢复。** 动作类型包含已有来源补读、条件扩窗、冲突核对、搜索新源、解释来源范围限制。核验建议也必须经过统一选择器；有明确本地候选时先补读，已读同范围不重复。原始来源约束始终保留。查明“来源不规定”时给出经过的章节范围和依据，不能仅凭一次没命中就作全文否定。

预期：降低有文档却无依据的假缺口、跨章节串用和无效搜索；这是质量与成本同时可能受益的一批。需要实测，不预报百分比。

### 第二批：让交付落实已确认的规则

4. **按要点组织证据包。** 每条命题携带来源版本、章节、精确引用、条件/例外和事实/建议属性；写作按要点取材料。来源长时优先保证核心要点，不按来源平均切块；超过预算显式标出遗漏并定向补读。已有核验事实及增量机制继续复用。
5. **决策表驱动有约束的设计回答。** 对重试类题先生成“方法×故障→许可条件、等待、停止”表，再据同一规则生成伪代码和结论；扩展到诊断题用“现象→证据→判断→措施”，比较题用“维度→版本→结论”。只在任务适合时启用，避免所有问题强行套表。
6. **一次交付检查，按反例做局部修订。** 检查核心命题与原文支撑、结论与正文一致性、代码各路径是否落实用户约束；报错必须提供命题位置或一条反例路径。宿主只做能可靠确定的结构/预算检查，语义判断由现有复核承担；遇到高风险未决项再做针对性复核。不要执行任意模型生成代码，也不要用新变量名正则继续打补丁。修订后检查受影响规则及必要关联部分，不反复全量重审研究材料。

预期：减少“解释正确而交付错误”、引用真实但不支撑命题、不同段落策略冲突。初期可能增加少量必要输出；以减少返工和错误为目标，不能承诺每题都更省 token。

### 第三批：用独立质量基线决定下一步

7. **保存必要审计产物。** 脱敏保存回答契约、各阶段可见证据、事实账本、初稿、局部修改、检查依据、最终回答及 usage，避免保存 API Key 或无关敏感配置。
8. **三种模式共同验收。** RFC、Python 版本诊断、跨语言比较，加未见过的长文和普通开放问题；每题预先准备人工核对的最小事实/条件、允许建议和反例。冻结来源、模型配置与预算，旧版/新版同题配对各至少三次；再用独立开放搜索测试来源获取能力。分别报告事实支撑、核心要点覆盖、版本/条件准确性、交付约束违例、假完成/假缺口、调用数、输入输出 token、耗时，不能只报平均总分掩盖严重错误。
9. **分批消融，避免一次改完无法归因。** 顺序比较基线、只改定位/补读、再改契约、再改交付检查。先要求本轮两个已确认错误不再出现、关键章节进入材料、Python/跨语言题不退化；随后再评估更广样本。在输入证据与预算一致后，才比较模型能力与模式差异。

这些改造落在规划契约、材料检索、恢复、写作和评测的共用组件，覆盖三种模式；Workflow 的固定步骤、Plan-and-Execute 的依赖推进、Multi-Agent 的分工并不需要合并为一种策略。

## 本轮交付校验

- 已按来源正文计算 SHA-256，并用事件里的哈希筛选核验可见范围。
- 已逐项比对关键条款坐标、写作窗口、最终回答与复核输出。
- 已对照原规范确认 413/503 归属及幂等自动重试依据，并阅读上述论文摘要、固定版本源码和官方工程实践。
- 仅新增诊断报告和审计数据，没有修改运行代码或重新跑模型。因此当前生产质量问题仍然存在，以上收益均待后续实施与对照验收。
