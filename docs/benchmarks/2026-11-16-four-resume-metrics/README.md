# 四条简历能力的分别验证

本报告补齐“稳定性、预算、证据、评测”各自对应的验证结果。不同指标来自不同实验，不能混成生产成功率或把受控场景通过率当作自然故障恢复率。

## 一、执行稳定性与故障恢复

**8项故障场景回归全部通过，耗时8.33秒。** 使用可控模型/工具响应配合真实执行代码和SQLite存储，无外部模型故障恢复率推断。原始结果见 stability.xml，选定测试及结果见 measurements.json。

| 场景 | 被验证的行为 |
|---|---|
| 分支异常 | 失败分支不会抹除成功分支的证据，整体保留未完成状态 |
| SQLite中断恢复 | 新图实例从检查点继续，已完成分支仍只调用1次，中断分支共调用2次 |
| 瞬时模型超时 | 一次瞬时失败后重试成功，共2次调用 |
| 持续工具错误 | 按配置最多3次尝试后停止，不无限重试 |
| 工具致命错误 | 只调用1次，不重试 |
| 工具超时 | 正确终止、记录错误及预算，不暴露原始敏感信息 |
| 调用取消 | 已消耗预算在恢复后继续保留 |
| 重复补查 | 拒绝重复查询，不再派发同一任务 |

SQLite实验只注入了一次中断并恢复一次。可以写“该中断恢复场景已完成分支重复执行0次”，不能扩写为“生产恢复率100%”或任意次数恢复都零重复。

## 二、预算治理与执行效率

**6项预算边界回归全部通过，耗时2.90秒。** 原始记录见 budget-boundary.xml：

1. 任务模型调用上限在供应商派发前生效。
2. 并发调用原子预留，不能共同突破运行级额度。
3. 输入Token限额生效，同时保留Writer可用预算。
4. 在既有总调用上限内为最终生成及审查保留调用。
5. 研究时限与收尾窗口分别生效（使用注入时钟验证边界）。
6. 恢复后沿用原运行预算，不借新配置扩大额度。

此前8题、16次真实运行均未超过20次模型调用及100000输入Token；所有完整任务耗时也均低于600秒。这里没有实际抓取网页，不能将这批冻结语料结果解释成网页抓取预算压力测试。

效率的准确结论见上一轮真实对照：总体平均输入Token **16.1k→18.1k，增加12.4%**。因此不能写平均Token下降。可以使用明确的单项多跳用例：模型调用 **15→8**、输入Token **52108→19902**，两组均通过参考验收；必须保留“单项用例”限定。

## 三、证据与上下文治理

### A. 真实运行的结构与来源一致性

从前一轮16次运行的最终产物直接核验，逐条结果在 evidence-checks.json：

| 观察项 | 基线8次运行 | 优化组8次运行 |
|---|---:|---:|
| 已接纳的证据片段记录 | 51 | 64 |
| 片段与正文坐标逐字匹配 | 51/51 | 64/64 |
| 片段版本、记录哈希与正文SHA-256一致 | 51/51 | 64/64 |
| 最终来源引用能回溯active证据记录 | 7/7 | 11/11 |
| 通用无实质内容兜底 | 3/8 | 1/8 |

片段记录可能在不同finding间重复，不是115个独立事实。统计对象是已经接纳并保存的片段，无法反推原始模型提案通过率。两种配置都已有宿主证据校验，不能据此声称优化让引用正确率从较低值提升到100%。

**逐字一致验证来源，不验证片段是否在语义上支持结论。** 原始8题的语义评分存在内部不一致，因此没有发布自然幻觉率或语义引用支持率。

### B. 真实模型的已知错误纠正实验

为得到证据机制的直接效果指标，另做 **8个受控错误注入场景**，调用生产 review_answer 模块及真实 kimi-k3 服务。合成资料与错误草稿在 evidence-injection/cases.json 中提前固定，每份草稿包含一处已知错误和一个正确对照要点；预期答案没有单独传入模型。

| 已知错误类型 | 纠正结果 | 正确要点保留 |
|---|:---:|:---:|
| 把p50值误当p95 | 是 | 是 |
| 将JSON支持扩大为strict支持 | 是 | 是 |
| 最低版本错误 | 是 | 是 |
| 忽略周一闭馆例外 | 是 | 是 |
| 字段归属对象错误 | 是 | 是 |
| 编造20%性能改善 | 是 | 是 |
| 数字事实正确但引用错页 | 是 | 是 |
| 混淆免费与付费保留期 | 是 | 是 |

结果：**已知错误纠正8/8、正确对照要点保留8/8、整体删除答案0/8**。真实模型调用8次，实际输入9015、输出737 Token；用量均完整，无格式修复重试。回答和评估见 evidence-injection/各场景目录及 assessments.json。评价由本助手按预设合成事实复核，不是独立人工标注。

案例“编造20%性能改善”修正后明确说无法得出该比例，同时保留支持批处理的事实；否定引述20%不算继续主张该收益。其unanswered_points仍保留没有测量数据的限制，纠正成功不意味着补出了不存在的数值。

这证明该审查模块在这些简单已知错误场景有效；不能写成“自然幻觉率降低100%”“所有错误都可纠正”或完整Agent端到端成功率100%。也没有单独对长上下文选择策略做消融，不能将结果全部归因上下文机制。

## 四、可观测性与评测

前一轮固定8题（六类技术文档任务）、两组16次真实运行：

- 严格参考验收通过：**2/8→5/8，即25%→62.5%**。
- 预置验收项通过：**13/25→21/25，即52%→84%**。
- 供应商用量记录完整：**16/16**，失败/部分完成任务不从统计中删除。

使用匿名同模型评审加本助手复核，不是独立人工双标或统计显著性结论。本轮主实验保存本地可审计产物，没有依赖托管LangSmith实验上传；项目已有LangSmith集成能力与本轮实际记录方式需区分。

完整对照协议、原始回答、逐题评分与成本见 [8题真实对照报告](../2026-11-16-eight-case-live/README.md)。

## 推荐简历用词

- 稳定性写“8类受控故障回归通过”，不写线上恢复率100%。
- 预算写“6类边界验证通过、16次运行预算超限0次”，效率下降数字仅用于明确的单项用例。
- 证据写“8个已知错误注入草稿全部纠正，正确要点均保留”，不写自然幻觉率下降100%。
- 评测写“8题开发样本的严格参考验收通过率25%→62.5%”，不写通用复杂任务成功率62.5%。

这些是实际执行后的分项验证结果，全部原始记录与脚本保留；没有将受控机制测试冒充线上效果实验。
