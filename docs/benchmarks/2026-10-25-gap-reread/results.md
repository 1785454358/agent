# 缺口驱动的原文回读：实现与实测

本轮接通了“核验发现缺口 → 补读已有原文 → 重新核验 → 必要时搜索”的执行闭环。固定失败材料中的新增段落确实进入了核验和写作；完整联网 SQLite 题也给出了上一轮遗漏的读者结束标记与 checkpoint 推进机制。但 LangGraph 题仍出现“研究核验全部覆盖，写作审查发现未回答事项”的分歧，不能据此宣称已经达到成熟产品的稳定质量。

## 实现改变

此前补查提示允许“优先读取已有来源”，实际计划却只有搜索查询，执行器无法执行回读。本轮让 Workflow 选择已有来源的真实 `block_id`；主程序把它解析为来源 ID、版本、哈希与字符范围，实际调用 `read_evidence`。导航预览不作为事实，正文不进入图状态。来源资格仍由核验决定。

- 导航最多 8 个当前来源、每来源 32 个段落、总计 128 个，按来源轮流分配；长页均匀抽样，超长不可分段及省略项记录诊断。预览最多 200 字符，标题和 URL 也有上限。目录可能遗漏关键段落，这不是完整阅读承诺。
- 最多一个回读阶段、两段，每段不超过 900 字符。读取前复核当前授权、版本和哈希；只允许指向封存需求中的实际缺口。覆盖项、未知编号、重复或失效动作无法获得新证据权限。
- 回读走现有 ToolGateway、预算与 Ledger；断点续跑复用计划，相同调用重放不重复消耗预算。取消会向上传播，单个来源复核失败成为可恢复的读取缺口。
- 新读的完整范围优先进入原有核验窗口，每来源预留最多 2000 字符且至少留出 1000 字符给其他材料；全局 token、来源、短引用数量上限不变。实际引用不足以连续覆盖整段时不能把整段视为已读。
- 回读后重新核验；缺口已解决则取消备用搜索，部分解决则去除已覆盖的目标。仍有缺口且没有备用搜索时，最多再做一次搜索规划；新搜索阶段仍只有一轮、两条查询。
- 其他策略默认继续使用原来的搜索补查协议。模型、思考配置与共享上限没有提高：20 次模型调用、100000 输入 token、240 次工具调用。

实现主要在 `strategies/source_reread.py`、`strategies/workflow/reread.py`、`workflow/recovery.py` 与现有核验材料装配器。没有修改依赖、替换底座、部署或提交代码。

## 固定原文重放：保留失败，再修复协议

固定输入来自上一轮 `release-check/sqlite` 的四份已引用官方原文、全部可用的实际读取锚点、封存需求、已接受结论及原有 r3 缺口。入库后核对来源 ID 和正文哈希一致；三次重放的初始材料及业务状态一致，仅 run/thread ID 改变。没有手写新的事实、目标段落、覆盖结果或模型答案。

每个阶段只生成一次。规划、核验与写作使用生产模型网关及其共享预算；读取使用生产 ToolGateway。没有再次联网取材，没有重新执行前半段研究；因此这些耗时不代表完整请求耗时，也不与联网题直接比较。

固定重放各自使用新运行的预算，只统计新增调用，没有重建上一轮原请求已经消耗的预算和期限。后面的两道联网题则从完整请求入口执行并使用该请求的共享预算。

| 阶段 | 秒 | 新模型调用 | 工具调用 | 自动结果 |
|---|---:|---:|---:|---|
| 原有材料直接重新核验/写作 | 13.335 | 3 | 0 | r3 missing，部分答案 |
| 首版回读实现 | 14.106 | 4 | 2 | r3 missing，部分答案 |
| 修复短引用合并后，重放同一份真实回读计划 | 10.752 | 3 | 2 | 4/4 covered，无 partial_reason |

首版失败不是“模型又没理解”：两次工具读取成功，但工具会将大于 500 字符的段落编号为多个短引用。首版执行器只接受与请求整段坐标完全相同的单一锚点，错误地丢弃了这些真实片段。现已改为：只有相同来源、版本和哈希的实际片段连续且完整覆盖请求范围，才恢复该整段的读取锚点。先添加失败回归，再修复；缺失任意片段仍不能通过。

修复后的重放**复用首版模型已经生成的两条回读动作**，没有重新抽取一个更好的规划答案；这可以更直接检查执行器修复。重新核验和写作仍为真实新调用。它补入了“始终存在活跃读者时 checkpoint 无法完成、WAL 会持续增长”的原文。该段落在首版核验和 writer 输入中均不可见，修复后在两者中可见。

这个固定样本仍有实质局限：回读导航没有抽到解释 reader end mark 的完整因果段，模型选择的另一段是历史大事务限制及其后续修订。最终自动覆盖通过，**不代表已读到全部机制，也不代表每个分句都独立验证正确**。固定重放的回答对 RESTART/TRUNCATE 的完成、等待与 BUSY 条件仍表达得过于压缩。见三份原始答案：[直接核验](outputs/frozen-before.md)、[首版失败](outputs/frozen-initial-after.md)、[协议修复重放](outputs/frozen-protocol-fix-after.md)。

两个问题、配置、实际 usage、各阶段结果见 [runs.json](runs.json)；完整回答见 [LangGraph](outputs/network-comparison.md) 与 [SQLite](outputs/network-sqlite.md)。模型网关返回的 provider 名为 `deepseek-v4-1-flash-261017`，配置名仍为 `deepseek-v4.1-flash`；这些实际调用的 reasoning usage 为 0。

SQLite 回答包含：WAL 仍会返回 SQLITE_BUSY、单写者、读者结束标记阻止 checkpoint 推进的原因、进度续接、网络文件系统与 page_size 限制。此次关键机制确实出现在最终文字中。但未做独立专家盲评，引用协议与覆盖率不能替代逐句准确性评价。

LangGraph 回答保留了 checkpoint / Store 的线程边界及 `Command(resume=...)`，没有再次把 Store 和 checkpointer 都写成编译的强制前提。但仍把 Store 后端的进程重启保留条件列为无法确认，也没有清楚说明 interrupt 恢复时从节点开头重跑的副作用边界。写作审查正确保留了未回答事项，研究核验却提前把六项需求全判 covered。新增研究回读依赖研究阶段暴露缺口，**尚未把写作阶段新发现的缺口送回研究**；这是本轮仍未解决的关键断点。

## 验证与边界

新增回归覆盖实际回读、备用搜索取消/筛选、无备用搜索时的有限恢复、原有搜索路径、失效版本/哈希、未知/已覆盖目标、预算耗尽、断点恢复、Ledger 重放、短引用连续覆盖与缺片拒绝、取消、来源复核故障、新窗口及 writer 支持传递。它们验证协议和调度，不给真实答案打准确率分数。

最终测试数量、日志、修改前后代码哈希、五次真实运行原始文件哈希及此前三轮 artifact 校验见 [manifest.json](manifest.json)。原产品比较与前两轮优化输出原样保留；本轮所有失败、中间结果和成功结果均列入记录。

- 后端离线全量：**1565 passed, 2 deselected**，78.13 秒。出现 4 条 aiosqlite 后台线程 `Event loop is closed` 警告，与上一轮观察到的警告同类；根因没有在本轮定位，不声称已修复。初次全量的 1561 项结果也保留在日志中。
- 独立评估环境：**66 passed**，5.22 秒；本轮没有修改该评估包。
- 新增 23 项回归单独执行通过；Scoped Ruff、空白检查及对照本轮修改前副本的代码复核通过。复核检查了来源授权、引用完整性、预算、重放、取消和旧协议兼容。

下一处应优先处理研究核验与写作完整性之间的分歧，并改进长页导航的召回。扩大自评覆盖率或再加一层同模型“确认正确”不能证明这些问题已经解决。
