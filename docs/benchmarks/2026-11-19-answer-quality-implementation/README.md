# 证据定位与交付质量：实现及验收

本轮按[质量诊断](../2026-11-19-answer-quality-diagnosis/README.md)的顺序修改共用链路。覆盖 Workflow、Plan-and-Execute 和 Multi-Agent，不合并它们各自的执行策略。

## 已实现

### 定位和补读

- 新增 `tools/source_sections.py`：对 Markdown、明确编号章节、RFC 抽取标题、带 ¶ 标记的 API 签名建立原文字坐标索引；忽略代码围栏中的伪标题和目录点线。未知版式继续用段落定位，不把启发式索引当作事实证明。
- `tools/evidence_views.py` 保留命中片段的所属标题，避免跨章节打包；短且明确匹配的章节在原预算内整节读取，保留条件和例外。具体 API 的查询不因通用章节关键词而被宽泛章节抢占；前提问题优先保留完整条件列表。
- `strategies/evaluation_materials.py` 为阅读组提供章节导航，明确导航不是可引用证据编号。接受的事实仍需实际原文引用、版本、哈希和范围验证。
- `strategies/source_reread.py` 不再让超长单元从补读候选消失，提供有界窗口并保留不完整诊断；明确本地章节可先补读，已读同版本范围不重复。章节只有标题时不把它当作已读规则正文。
- `supplement_plan` 在处理核验器的搜索建议前建立本地导航；带建议的路径也可返回实际补读动作。范围内无明确本地候选时保留模型恢复选择与备用搜索。
- 实测又发现复用来源会绕过发现阶段的阅读词初始化；`harness/batch_collection.py` 已在该路径沿用任务的原文定位词。无新定位词的旧任务保留旧单次阅读行为，避免增加无效工具调用。

### 事实契约

- 规划支持 `fact / design_criterion / constraint / output_criterion`；只有事实进入封存覆盖，其他类型保留为交付标准。
- 紧凑任务同时引用已声明的事实和交付标准时，保留事实映射，不因多了非事实编号而整份降级。未知编号仍拒绝，不丢弃真实用户范围。
- 没有额外研究简报的紧凑规划也保留其交付标准；原始问题始终独立传递。
- 规划指令区分规范事实、自行提出的默认策略和否定约束；没有把 `allow_unknown` 全部改为 true，也没有把“没搜到”自动当成完成。

这里是结构与指导的改善，不是宿主能自动识别任意自然语言分类错误的承诺。真实模型仍会把部分设计问题混入事实需求，见下方验收限制。

### 交付一致性和可追溯复核

- 有条件判断的设计题先组织“对象×事件→前提、动作、停止条件”，再据同一规则写代码和结论；诊断、比较任务分别组织证据链及版本维度。
- 原有一次终审中新增最多四条重点检查：事实附答案片段和原文短引，行为附具体输入、分支与结果；不运行模型生成代码。
- 宿主校验检查记录能否追溯到修订后答案及实际可见来源。原文匹配仅忽略布局空白，保留词、标点和 MAY/SHOULD 等差别；不接受同义改写冒充逐字引用。
- 审查附属记录独立有界解析。多余、无效或无法追溯的记录不能获得 passed，也不再导致整篇有效修订丢失；保留诊断并使复核保持未完成。条目超限优先保留报告出的未决反例。
- 已有编辑唯一性、重叠、引用编号、预算和代码约束校验仍执行。超长修订可在同一两次上限内请求一次定向缩短，不裁断代码；修复机会耗尽仍不声称通过。
- 事件保存原稿、原始复核返回、修订结果、具体问题、有效检查及诊断，便于区分写作与修订引入的问题。旧协议允许没有新检查字段，其记录会显示 `witnessed_review=false`，不能据此宣称已经完成逐条证据审查。
- 增量核验的规则摘要包含新章节模块，避免规则变化后继续复用旧判断；既有 full/delta/reused 调度保留。

**重要边界：宿主验证的是追溯关系及已编码约束，不是任意命题的逻辑蕴含。带引用的检查记录仍可能在语义上判断错误。**

## 验收方式

先用失败用例复现，再修改实现并回归。新增/扩展用例覆盖：标题丢失、章节条件遗漏、API 签名归属、代码伪标题、授权阅读边界、超长块消失、补查建议绕过补读、已读范围去重、非事实契约丢失、复用来源的定位词丢失、虚构复核片段、引文模态改变、布局差异、附属记录超限、修订长度超限。

最终代码全量离线后端回归：**1881 passed、1 real 测试 deselected、33 项依赖警告，159.17 秒**；`git diff --check` 通过。真实模型验收单独执行，工程测试数量不计作语义正确率。

完整统计与源代码指纹见 [measurements.json](measurements.json)。运行命令：

```powershell
backend/.venv/Scripts/python -m pytest backend/tests -q -m 'not real'

# 在 backend 目录运行；输出目录必须是新的目录。
.venv/Scripts/python scripts/benchmark_frozen_efficiency.py `
  --sources ../.local-artifacts/http-retry-frozen-sources.json `
  --question ../.local-artifacts/http-retry-three-modes-20261118-efficient-v4/question.txt `
  --output ../.local-artifacts/my-quality-run
```

冻结测试使用真实模型和实际 provider usage，关闭外部搜索/抓取，资料原文保持相同。HTTP 比较三个模式；另用原 Python 3.11 诊断题测试 Plan-and-Execute、跨语言题测试 Multi-Agent。没有更换模型或修改凭证来获得更好的数字。

历史批次未保存足够的配置和统计重复，不能把历史前后单次耗时/token 差异解释为严格因果收益。调试失败和重试保留在工作区；没有将失败批次算成质量通过，也不将一次完成状态当成准确率。

## 质量结论与剩余问题

本轮确实修复了材料与协议层的缺陷，但**不能宣布三种模式的最终回答质量全部通过**：

- HTTP 新样本中的 503 已使用 MAY；Plan-and-Execute 和 Multi-Agent 的 429/503 代码分支显式保护未获保障的 POST。它们仍有事实覆盖不足、规范表述不完整或前提归属不准确的问题。
- Workflow 有一轮状态为 completed，首段仍将“业务可接受重复”作为重试理由。按本项目本题的保守 POST 验收口径，此项是质量失败。原有正则把同一句中的否定与另一分句的正向放行混在一起，模型终审也没有稳定纠正首句。没有把这个状态涂成“通过”。
- Python 与跨语言题继续按实际覆盖报告缺口。尤其需要检查 API 阅读单元与复合需求拆分后的覆盖；API 签名索引是本轮实测发现后补入的修复，不能只凭 RFC 样本推广结论。
- 规范的 SHOULD 与三次自动尝试之间的解释、过去 HTTP-date 的处理、版本边界和“本次没读到”与“规范未规定”的区分，仍需逐项验收。新增追溯检查不能取代这些语义检查。

下一步应以这些已保存失败样本为固定质量用例，针对首句、规则表和代码的同一策略建立可校准的约束核对；同时为不同类型的需求建立独立标准答案。开展相同配置、配对多次及消融比较后，再决定是否调整模型和预算。当前材料不足以支持“整体质量提升某个百分比”或“全部 partial 已解决”的说法。
