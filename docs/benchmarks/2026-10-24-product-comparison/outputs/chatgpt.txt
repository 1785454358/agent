LangGraph Checkpoint 与 Store：用途、线程边界与恢复能力
结论

Checkpoint（检查点）负责恢复某个 thread 的图执行状态；Store（存储）负责保存可供不同 thread 共享的应用数据。两者互补，不能简单互相替代。

根据 LangChain / LangGraph 官方文档，最重要的区别是：

Checkpoint = 执行状态持久化。 保存图状态快照，支持同一线程的对话延续、interrupt 后恢复、故障恢复，以及检查历史状态和时间旅行。

Store = 跨线程的数据持久化。 在图状态之外保存应用定义的数据，例如用户偏好、已知事实和共享知识；不同线程可以通过相同的存储命名空间访问这些数据。

两者组合 = 完整的持久化方案。 用 Checkpoint 恢复当前任务的执行进度，用 Store 提供跨会话的长期记忆。

官方依据：LangGraph Persistence（官方持久化文档） 。

GitHub

推断： 如果应用需要在部署升级、容器重建或机器故障后继续任务，应该把持久化后端、线程标识管理和任务恢复入口一起设计，而不是仅仅把 checkpointer 参数传给 compile()。

无法确认的事项： 仅凭使用了某个持久化后端，不能断言任何故障下都一定零数据丢失。具体保证还取决于数据库可用性、事务与持久化配置、数据保留策略，以及应用何时确认任务提交成功。

2. interrupt() 暂停后恢复

例如，一个审批 Agent 执行到人工审批节点，调用 interrupt() 暂停，等待用户决定是否批准。

Checkpoint： 这是恢复流程的关键。图需要配置 Checkpointer，暂停状态才能被保存。之后提供恢复输入，并使用同一个 thread_id 调用图，才能沿着原线程的执行状态继续。

Store： 可以保存审批规则、用户偏好或业务记录，但仅有这些数据不能恢复被暂停的图。它不知道原图执行到了哪个节点，也不保存 Checkpoint 所承担的恢复信息。

事实： 官方的 Thinking in LangGraph  示例明确展示了编译时配置 Checkpointer、使用 interrupt() 暂停，再通过 Command({ resume: ... }) 和同一线程配置恢复执行。文档还说明，中断节点在恢复时可能从节点开头重新执行，因此中断前的副作用需要谨慎设计。
Docs by LangChain

推断： 如果审批任务需要跨天、跨部署实例甚至跨机器恢复，那么应采用持久化 Checkpointer，并确保恢复请求能找到原来的 thread_id。Store 可以保存审批业务数据，但不能替代这套恢复链路。

无法确认的事项： 不能笼统承诺所有外部副作用都只执行一次。例如，节点调用外部支付服务后、成功结果写入检查点前发生故障，恢复时是否会重复调用，取决于具体执行位置和应用的幂等性设计。Checkpoint 不等于端到端的“恰好一次”事务保证。

3. 跨线程共享

假设用户在 thread-A 中告诉 Agent：“我偏好简洁的回答。”之后在 thread-B 开始新的任务。

Checkpoint： thread-B 不会仅仅因为 thread-A 保存过检查点，就自动继承 A 的对话历史和图状态。每个线程有自己的检查点序列。

Store： 如果 A 将偏好写入 Store，而 B 使用相同的 Store 后端、命名空间及键读取这条记录，B 就可以取得该偏好。

两者结合： A、B 各自保存任务进度，同时共享用户级长期记忆。这通常是多会话 Agent 更合适的架构。

事实： 官方明确把 Checkpointer 定义为线程作用域的状态持久化机制，把 Store 定义为跨线程长期记忆机制。Store 的读写发生在节点或应用代码中，并不是把一个线程的 Checkpoint 自动复制给另一个线程。参见 Persistence 。
GitHub

推断： 在多用户系统中，建议使用类似 user_id 的稳定业务标识组织用户级 Store 命名空间，而不是直接把某个 thread_id 当作所有会话共享数据的唯一索引。这样可以明确区分用户级记忆和单次任务状态。

无法确认的事项： Store 的“跨线程”不等于“所有线程默认可读”。实际能否访问、数据是否隔离，以及不同实例能否看到最新写入，取决于命名空间设计、后端配置、权限和一致性语义。不能仅凭使用 Store 就认定多用户数据隔离已经做好。

例如，生产环境中可以采用以下设计：

使用 PostgreSQL 等持久化 Checkpointer，保存每个任务的执行状态。

使用持久化 Store，保存用户级长期记忆。

为每次独立任务分配稳定的 thread_id，为用户记忆使用独立的用户级命名空间。

对支付、发邮件等有外部副作用的节点，另外设计幂等键、重试策略和业务状态校验。

最后一点是工程建议，而不是 LangGraph 自动提供的端到端事务保证。

五、事实、推断与待确认事项总结

类型

	

可以得出的结论




官方事实

	

Checkpoint 保存线程级图状态；Store 保存应用定义的数据，适合跨线程共享。




官方事实

	

内存 Checkpointer 不支持进程重启后的检查点保留；interrupt() 恢复需要正确的检查点和线程配置。




工程推断

	

需要任务恢复和跨会话记忆的生产系统，通常应同时配置两种机制。




工程推断

	

应将任务标识与用户记忆标识分开设计，并为外部副作用实现幂等性。




无法仅凭文档确认

	

具体部署的持久化保证、故障窗口内的数据损失、Store 的读写一致性、权限隔离及外部副作用是否重复执行；这些都需要结合实际后端和应用实现核验。

最终判断： 如果你的核心问题是“程序中断或重启后，Agent 能否接着做原来的任务”，优先考虑持久化 Checkpoint；如果是“新的会话能否记住以前的用户偏好或共享知识”，优先考虑 Store。两种需求同时存在时，组合使用才是更合理的设计。
