# DeepResearch 项目对照与当前代码实测诊断

日期：2026-11-08。范围：当前工作树，包含用户已有未提交修改。只增加诊断脚本和结果，没有修改生产代码、默认配置或历史评分。

核心判断：当前主要问题在研究范围扩张、必要原文送达不稳定、写作/自审的语义判断，以及多阶段带来的耗时和失败面。预算、来源哈希、权限和恢复机制有工程价值，但这些机制本身不能证明答案回答了用户问题。

## 本轮实测方法

- 冻结资料：3 道开发题（single_hop-dev-02、comparison-dev-01、multi_hop-dev-02），Baseline/Workflow/Plan-and-Execute/Multi-Agent 各 2 次，共 24 次真实模型运行。选题在运行前固定，针对过去已观察的暂停前提、范围扩张、恢复条件遗漏；不是随机抽样基准。
- 模型：配置中的 deepseek-v4.1-flash，thinking disabled。冻结组每次最多 20 次模型调用、48 次工具调用、30 次 Provider 尝试、240 秒、3072 输出 tokens、2500 字符答案。问题最多并发 2 个，策略固定顺序，不能当作独占服务的速度排名。
- 使用真实模型、固定资料搜索/抓取适配器；与生产共用 batch profile 和最终事实审查。评测使用内存状态，没有测生产数据库恢复或长期记忆收益。
- 联网补测：既有 SQLite WAL、LangGraph 记忆/恢复两题，Workflow 各一次，真实 Tavily 和网页抓取。沿用 live CLI 注册额度：40 次模型调用、24 次工具调用、80 次 Provider 尝试、360 秒、4096 输出 tokens、2000 字符。与冻结组预算不同，单列。
- 组件诊断：额外 2 次真实最终审查调用，分别只补一段遗漏原文、只收窄 SQLite 需求清单。不是新的完整 Agent 运行。
- 没有重试筛选高分答案，没有新增自动质量裁判分数。下文内容判断来自对原始输入、输出、原文的逐项检查，不等同于独立专家标注或总体准确率。

| 配置 | 运行数 | completed | answered | p50 秒 | 模型调用合计 | 模型调用中位数 | 工具调用合计 |
|---|---:|---:|---:|---:|---:|---:|---:|
| baseline | 6 | 5 | 5 | 14.04 | 11 | 2 | 24 |
| multi_agent | 6 | 4 | 4 | 34.91 | 44 | 6 | 78 |

completed/answered 为内部执行标记，不是语义准确率。p50 包含失败与部分完成运行。Baseline 的一个调用出现 LengthFinishReasonError（达到 3072 输出 token 上限），该次 usage 未完整返回；observed token 合计只代表已观测量，费用未知。

重要反例：

1. 同一副作用题的 Plan-and-Execute 两次分别 6/14 次模型调用、37.06/59.24 秒，均 completed；Multi-Agent 分别 5/14 次调用、37.22/54.62 秒，第二次 max_follow_ups_reached。多轮并没有稳定换来更好交付。
2. 简单暂停前提题中，Baseline 一次输出超长失败；另一次虽然 completed，却没有明确列出 interrupt payload 必须 JSON 可序列化。复杂策略保留原子需求有实际价值，不能据此直接全盘替换为 Baseline。
3. Workflow 比较题一次 11 调用/54.50 秒完成，一次 6 调用/33.27 秒 answer_review_incomplete。后者已给出核心选型建议，却扩写为 Graph API 的迁移路径及 Functional API 的图形可视化缺口。
4. 副作用题 Workflow 两次都说明节点从头重跑，但遗漏恢复必须使用同一 thread ID；来源中的相关明确段落没有交付给最终审查。其他文档里出现的 drained-run same-thread 语句不能替代 interrupt 的必要条件原文。

## 联网实测发现

| 题目 | 状态 | 秒 | 模型/工具调用 | 观察 |
|---|---|---:|---|---|
| SQLite WAL | partial / answer_review_incomplete | 47.43 | 6 / 14 | 规划扩展用户范围，自审按扩展项报告未答 |
| LangGraph 记忆与恢复 | partial / budget_exhausted | 80.50 | 6 / 24 | 工具额度耗尽；伴随连接超时后浏览器页面过大的抓取失败；答案仍有概念错误 |

SQLite 原问题只要求长读事务与 checkpoint 的因果关系、SQLITE_BUSY、多写者限制及网络文件系统边界。规划额外要求 WAL 增长/截断、并发写请求排队方式、其他共享存储与锁语义。最终审查列出三个未答项，均围绕这些扩展内容。答案包含主要维度，却被扩展清单拖成 partial。

LangGraph 答案写出“Checkpointer 跨线程：复用同一 thread_id 即恢复同一检查点”。这把同一线程恢复与跨线程共享混在一起；同一答案对比表又说 checkpointer 作用域是单线程。最终审查没有消除这处内部矛盾。这里同时存在采集预算与语义质量问题，不能用提高工具上限解释全部失败。

## 两个受控组件实验

**补充必要原文：有局部支持。** 复用副作用题 Workflow 第一次运行的最终审查输入、原草稿、需求和来源，只向对应 Interrupts 来源补入同一冻结文档字符 6426:6894 的原文（含 same thread ID）。一次真实审查补写“恢复时必须使用与中断发生时相同的 thread ID”，unanswered_points 为空。它支持该病例的证据送达假设；没有证明整个系统已修复，其他措辞问题仍需检查。

**只收窄需求：未解决。** 复用 SQLite 原草稿和全部原文，只把最终审查清单改为原问题四个维度。一轮真实审查仍把“写请求排队细节”“非网络文件系统的多主机共享访问”列为未答。模型继续受到草稿中扩写的缺口影响。不能把精简 requirements 或换一段提示词当成已验证的修复。

组件结果、原始/候选输入及 usage 见 `tmp/project-review-20261108-components/`；两个实验各一次，不是端到端质量分数。

## 哪些复杂度值得保留

- ModelGateway/ToolGateway、调用上限、取消和超时、最小持久化、原文版本/哈希/坐标、合法引用校验、原始轨迹：维护运行边界与可追溯性，保留。
- 需求级核对：保留必要事实的细粒度检查；历史聚合契约实验已出现遗漏必要前提，不能简单全部折成“回答原问题”一句话。
- 当前 v3 已允许成功原文读取后跳过分支 synthesize；Workflow 已包含补读与补搜。文档仍有“Workflow 固定路径、不补搜”“每个分支集中整理”的旧描述，需对齐，避免针对旧架构优化。

## 哪些复杂度应收缩或隔离

- 三套面向用户的策略入口：作为实验后端有价值，作为用户必须理解的产品选项收益不足。建议一个默认研究入口，以有界 Workflow 作为简化对照；保留 PE/MA 做消融与确需依赖/并行的大题实验，不急着删除实现。本轮 PE 的执行标记最好，不能据此证明其答案质量最好，也没有证明 Workflow 应永久胜出。
- 可选自由工具循环与默认 batch 双轨：不要继续同时扩展两条主产品路径。自由循环作为实验/SDK 能力隔离，并固定评测 profile，历史已发生评测走错路径。
- 语义长期记忆、BGE-M3/Chroma、MySQL/Redis 分布式路径：若目标是个人技术资料研究，默认部署可先用单机和轻量记忆。现有证据没有证明这些能力改善单次答案；这是投入优先级判断，不表示它们已被证实导致回答错误。
- 可选范围审查：已有整轮实验未过回归，不建议默认打开或继续叠加同模型审查角色。
- 提示词中混用领域规则：简单前提题的规划消息约 4740 字符，包含科研综述、量子领域、日期等无关指令。按题型裁剪值得消融；提示词长度本身尚不能证明质量下降。

## 建议优化顺序与验收

### P0：把失败定位在具体信息边界

复用现有 anchors、reading groups 和轨迹；对每项必要事实离线检查：原文存在→已读取→评估可见→Writer 可见→答案覆盖。不要把 URL 命中率、引用合法率或 completed 当作事实覆盖。

优先修复已复现的恢复条件段落送达。保护必要引用的上下文与同段条件，并避免 Writer 再次选段时把关键条件丢掉。当前代码已支持 support-first 与分组，问题是其未稳定覆盖全部必要条件；无需再造一套证据对象。

验收：同 thread ID、JSON 序列化、节点从头重跑三项都保留；对原始题和不涉及这些条件的题同时回归，不将无关知识硬塞到所有答案。

### P0：纠正范围扩张与完成判定

原始问题及必要前提应决定阻塞项。检索方向、研究建议和未问的实现细节不能因为规划器写入就自动升级为必须完成。保留必要原子事实；把扩展建议与真正未答分开记录。不能仅删除清单：本轮 SQLite 组件实验已证明草稿本身也会诱发假缺口。

验收：SQLite 的排队/其他共享存储扩展项不再阻塞原四维度交付；比较题不强制补齐两种 API 的完整对称迁移手册；暂停题仍检查 JSON 序列化。用这些具体反例检验范围规则。

### P1：控制自审的改写与失败影响

当前最终自审可以整体重写，且任何审查异常会落到来源列表兜底（responses/graph.py）。这增加最终答案丢失的风险；本轮没有实测到该特定异常分支，属于代码层面的交付风险。

将结构/引用协议校验与语义意见区分。对于已经通过必要校验、但复审服务不可用的草稿，可考虑保留有依据部分、显式标记复审状态；已知证据不支持的内容仍须剔除。不要把本轮建议理解成关掉事实核查或无条件返回原草稿。

比较题输出应给出有界综合判断，不要求来源逐字写出同一张比较表。对比“当前复审”“仅修明确错误、限制整体改写”的受控候选，逐题看必要事实是否保留，以及错误是否真的减少。

### P1：在不损失必要事实的条件下减少调用

简单 Workflow 已出现 planner 1 + source selection 2 + evaluator 1 + writer 1 + review 1 的 6 调用路径。优先消融每分支选源调用与重复阅读，而非增加 Supervisor。先固定必要事实覆盖，再比较调用量、耗时与局部退步；不凭完成率或少两次调用宣布优化成功。

### P2：缩小产品场景并校准评测

先选技术官方资料核查/比较作为核心场景，通用科研年度综述单独维护题型和来源策略。研究型框架与用户产品目标分开：一个主入口、清晰报告与可展开证据，比让用户选择三种编排术语更容易评估。

下一轮固定少量人工核查必要事实的开发题，覆盖事实、比较、多跳、版本、冲突与合理拒答；每题重复，保持源、模型、预算和评分身份一致。候选稳定后再使用未参与调优的测试集。本轮三题诊断不能替代该验收。
