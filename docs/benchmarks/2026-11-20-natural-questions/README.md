# 自然提问联网评测基线

这组题用于比较统一研究 Runtime 的改造前后表现。面向用户的输入沿用日常提问方式，后端只收到 `inputs.question`。评分侧另存参考要点、来源和固定评审日期。当前方案以这 6 题替代此前长题面作为后续迭代基线，历史报告保留原题与原结果。

| 场景 | 用户提问 |
| --- | --- |
| 行业研究 | 调研一下全球和中国的大模型推理芯片市场规模，以及未来三年的增长趋势。 |
| 行业研究 | 全球和中国的工业机器人装机量这几年增长得怎么样？ |
| 竞品分析 | 我们想把团队知识库从共享网盘搬出来，Notion 和飞书文档怎么选？ |
| 竞品分析 | 团队代码都在 GitHub 上，跑 CI 是继续用 GitHub Actions，还是接 GitLab CI？ |
| 技术调研 | 订单扣完库存，还没确认消息，消费者就崩了。Kafka、RabbitMQ 和 SQS FIFO 会怎么处理？我们已经在 AWS 上，该怎么选，怎么验证重投不会重复扣库存？ |
| 技术调研 | Python 里并发起了几个子任务，一个报错后其他任务还在跑，怎么让它们一起停下来并做好清理？ |

## 基线口径

- [版本化题目与评分参考](cases.jsonl) · [LangSmith 数据集](https://smith.langchain.com/o/d90581d5-a6ea-478d-9c45-9407e1a70582/datasets/2a43c9ee-79dd-4190-a500-ef2bcc6ee514)
- 查询快照时间为 `2026-11-20T05:36:08.949651+00:00`，题库 SHA-256 为 `0699d16f3a06fc32ea8e5d6c8c6858e234919461709391055ea3a5779a930c35`。基线以 2026-11-20 可得资料为评审参照，固定题目、参考和统计口径。环境为真实联网，网页和搜索排序仍会变化。
- 每题从新线程以 Auto 发起一次，使用现有生产任务适配器和 LangSmith 裁判。后续对照保持模型、预算、题库版本和裁判设置一致。评分侧以正确性和 Writer 原文支持度分开统计。
- 推理芯片和订单重投已用于故障诊断。整组适合做开发回归和版本对照。正式验收另准备未参与调优的题目。
- 评审允许可信的等价来源与合理的不同建议。涉及市场统计，区分相邻口径与严格口径。涉及产品选型，按场景约束核对建议。参考资料和评分标准仅用于裁判。
- 运行完成率以任务返回 `completed` 为准。语义验收沿用现有 v4 裁判，正确性和证据支持均须达到 0.8，并通过来源权限和预算检查。模型调用统计真实供应商请求尝试次数，Token 取研究任务本身的模型用量，不含独立裁判。

## 后续对照

按当前版、改进首轮版、首轮加有界补查版依次比较。核心指标保留正确性、证据支持和关键要求覆盖率，另记录首轮命中、补查触发与挽救情况，以及端到端耗时、模型调用和 Token。需要归因时，固定同一批检索结果做回放，并以真实联网复核取证效果。

## 首轮规划与补查对照

三个模式共用同一研究链路。首轮按独立事实和不同资料路径分配查询，留有名额时为未分配的事实补一条查询。完整改造在 Writer 之前检查实际读到的原文，仅针对缺口派发最多两条新查询，复用原有采集工具、运行预算和引用校验。冻结语料保持原有取证范围。

三组都用同一题库版本、模型、Auto 路由、预算和 v4 裁判，每题各跑一次。主表耗时和用量统计 `completed` 任务，验收率以全部六题为分母。用量包括输入和输出 Token，独立裁判的消耗单列在 LangSmith 轨迹。
