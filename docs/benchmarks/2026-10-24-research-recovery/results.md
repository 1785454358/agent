## 已落地的改动

| 观察到的问题 | 实现与边界 |
| --- | --- |
| 猜测的旧官方域名限制全部搜索，漏掉迁移后的文档 | 主搜索保持开放；补充搜索可用域名提示，多域名用 OR。规划器仅从用户明确给出的域名生成提示，其余通过搜索发现。来源资格仍需读原文核验。 |
| 搜索同名、无关网页占用抓取名额 | 将已有的有界候选选择扩展至普通 v3 分支，结合任务和需求选直接相关原始来源。只接受真实候选 ID，非法选择不派发抓取。 |
| 分支二次总结丢失已读原文，重复消耗上下文 | v3 分支直接交付原文读取锚点，由父级统一核验；候选选择替代原来的分支总结调用。分支读完不等于任务完成。旧协议保留兼容路径。 |
| 网页只有前 20,000 字符进入证据库，尾部条件永久丢失 | 抓取对象增加仅在调用期间使用的完整正文，证据库接收完整正文；序列化预览仍保留原长度上限。完整正文不进入对象序列化或 repr；HTTP 和证据库的既有大小限制不变。 |
| 核验器一边引用来源、一边判定同一来源不合格 | 用已有的一次语义修复额度反馈矛盾，要求重新判断来源并重写结论和覆盖。修复失败仍拒绝相应结论，不放宽引用、来源和覆盖校验。 |
| Workflow 首轮漏项后直接结束 | 基于封存需求补查最多一轮、最多两条新查询，复用原有授权、预算、补查目标验证和覆盖核验。拒绝重复查询、虚构需求及仅指向已完成需求的任务；预算耗尽不调用补查规划器。新计划重置补查状态。 |
| 流程题只有能力名，缺少具体调用 | 写作与审查保留原文支持的最小调用、参数和执行顺序，避免再次压成抽象总结。真实原题已出现 `Command(resume=...)` 及节点重跑说明。 |

## 未解决项与人工复核

1. **自动完成仍不等于事实全部正确。** LangGraph 最终答案在“跨线程共享”中写“图需同时用 checkpointer 和 store 编译”，把组合示例扩大成必需条件。[官方 Store 文档](https://docs.langchain.com/oss/python/langgraph/stores)允许独立使用 Store；这一表述过强。线程 ID 是状态索引边界，也不能据“线程间隔离”的简写推导出访问控制保证。
2. **同模型审查仍会漏错。** 对上述原稿及当次可见原文冻结复查，额外加入“示例不等于必要条件”等通用提示，实际一次模型调用仍返回原稿和空 issues。无效的两条试验指令已撤下；该复查单独记录，不计入主运行 7 次调用，也不声称问题已修好。
3. **SQLite 仍漏答。** 最终答案补出了 WAL 仍可能 `SQLITE_BUSY` 的场景及 checkpoint 接口条件，但未完整回答 rollback journal、长读事务影响及不适用场景。[SQLite WAL 官方全文](https://www.sqlite.org/wal.html)实际包含相关说明，不能将当次模型可见材料不足理解成官网没有答案。修复完整正文保留后，还需要改进读取窗口和跨段条件整合。
4. **本轮没有重新运行三家产品。** 产品输出仍是上一轮真实匿名模式记录，未用付费研究模式，也没有凭本轮单题改善重新排序。没有发布、部署或切换生产模型。

后续质量重点是需求与段落的语义匹配、保留整组条件，以及能发现“可以/示例”被扩大为“必须”的事实审查。当前工程修复可复查，但这两类模型质量问题仍然开放。
