# Token 与模型调用效率分析及改造建议

状态：已按批准方向实施首轮项目级改造，[实现与验收记录](../2026-11-18-token-efficiency-implementation/README.md)。成本已有实测变化，完整性与关键质量验收仍有未通过项。依据 2026-11-18 HTTP 重试题的真实调用轨迹与两个本地项目源码；不将单题结果外推成所有任务的稳定收益。

## 1. 为什么 GPT-Researcher 本次更省

### 实际调用构成

| 环节 | GPT-Researcher 标准报告：调用 / 输入 token | agent_new Plan-and-Execute：调用 / 输入 token |
|---|---:|---:|
| 角色选择、规划与查询生成 | 2 / 3505 | 2 / 5956 |
| 模型选择来源及生成读取词 | 0 / 0 | 3 / 8520 |
| 证据充分性核验 | 0 / 0 | 2 / 12576 |
| 单独的缺口补查规划 | 0 / 0 | 2 / 15156 |
| 写作及最终复核 | 1 / 13928 | 2 / 7856 |
| 合计 | **3 / 17433** | **11 / 50064** |

GPT-Researcher 本次三次调用对应选择研究员角色、生成检索查询、生成报告。网页搜索、抓取、文档切块和本地嵌入筛选不逐页调用聊天模型。标准报告没有经过与 agent_new 相同的逐项覆盖核验、补查决策和独立事实复核回合；不能据此断言它的 deep 等模式也只需三次调用。

最重要的区别是中间控制过程的频次和输入内容。Plan-and-Execute 的核验与补查规划共使用 **27732 输入 token，占 55.4%**；Workflow 是 58.0%，Multi-Agent 是 55.5%。补查规划一次输入约 7–8 千 token，输出却只有约 140 token 的少量查询。多次传输规则、Schema、已知情况、失败诊断与旧材料，构成主要开销。

最终写作本身并非 GPT-Researcher 更小：它的一次写作输入为 **13928**，比 Plan-and-Execute 的起草与复核合计 **7856** 还多。故优先优化中间重复控制成本，不能只缩短最终答案或写作材料。

### 本地检索节约了什么

本次 GPT-Researcher 抓取的文本共 556746 字符。其检索入口逐篇截取前 50000 字符，进入后续处理的文本最多约 159140 字符；再经过约 1000 字符分块、100 字符重叠及本地 MiniLM 相似度筛选，研究上下文约 43674 字符。这个过程中没有新增聊天模型摘要调用。

这里的嵌入用于本轮文档取段，和长期对话记忆是不同用途。它把一部分计算转到本地 CPU/内存，并非完全没有成本；本次实例初始化约 10.69 秒，脚本冷启动另有约 45 秒模块导入。

本次三次 GPT-Researcher 调用的 `cache_read` 均为 0。节省不能归因于提示词缓存；缓存折扣也不能和原始输入 token 数下降混为一谈。

### 对照限制的修正

全局配置虽然是 temperature=0，但 GPT-Researcher 的原生调用代码分别使用 0.15（角色选择）、默认 0.4（查询生成）、0.35（写作）；agent_new 使用 0。此前“全部调用同温度”的表述已修正。调用数与 usage 数值不变，但质量和耗时不是严格同参数消融结果，后续验收应记录实际请求参数。

## 2. 哪些值得借鉴

| 做法 | 是否借鉴 | 在现项目中的处理 |
|---|---|---|
| 一次生成互补查询，然后批量抓取 | 值得 | 批量工具执行已存在；重点减少每个分支重复进行的来源选择与规划调用。 |
| 用本地文档分块、检索、去重替代逐页模型摘要 | 值得 | 当前也已有关键词取段；在此基础上增加按章节检索与可选语义排序，继续保留真实原文和坐标。 |
| 相同资料在多个步骤之间复用 | 值得 | 工具缓存已存在；需要新增的是核验结果及其依赖快照的复用，避免把缓存抓取当作已经缓存核验。 |
| 收集资料后直接生成最终报告 | 不作为默认路线 | 本题 GPT-Researcher 的 POST 429 与等待时间代码出现实质错误，应保留关键检查。 |
| 逐篇只保留前 5 万字符 | 不采用 | 本次 RFC 9110 的非幂等重试条款约在第 161053 字符、Retry-After 语法约在第 204673 字符，均在检索分块前被排除。应检索整份受限存储的文档，而不是只处理前缀。 |
| 相似度高就作为合格来源或覆盖成功 | 不采用 | 相似度只用于找段落；来源约束、版本、事实支撑和覆盖仍须单独校验。 |

现有项目已有批处理、本地关键词取段、引用校验、预算、补读和无进展退出。方案应复用这些能力，改进触发条件和传输内容，避免再造一套执行流程。

## 3. 三种改造路线

1. **仅精简提示词与 Schema。** 改动最小，能减少每次输入；重试、重规划、全量核验次数基本不变，收益有上限。
2. **保留三种策略，合并重复决策并按变化核验（推荐）。** 批量取证后集中核验；核验同时提出有限恢复动作；后续只处理受影响的需求和新增原文。保留最终关键检查。
3. **整体采用收集后一次写作的标准报告流程。** 调用可很少，但会削弱独立覆盖核验与约束检查，也不能保持现有三种策略的完整特点，不建议作为当前默认方案。

推荐第二条，第一条作为其中低风险的起步工作。动态路由和手动模式覆盖继续保留，Workflow、Plan-and-Execute、Multi-Agent 的顺序、依赖和并行分工不合并为同一条执行图。

## 4. 针对问题、方案与预期效果

| 针对问题 | 拟采用方案 | 预期效果及边界 |
|---|---|---|
| 大文档整份失败，补查反复寻找同一资料 | 保留下载、解析时间和体积上限；优先跟随已发现且获授权的 HTML/TXT/章节链接。长文按章节/段落建立索引，在预算内读取相关节。PDF 采用受限的页段提取方案，明确未读取页，不把部分提取当全文。 | 先提高取得关键原文的能力，减少无效重搜；质量提升优先，模型输入不一定立即下降。不会简单取消全部大小限制。 |
| 规划结构复杂，查询在多个字段重复导致额外修复 | 模型只输出需求与一个规范任务数组（任务 ID、查询、需求 ID、读取词）；由宿主生成现有映射和展示数据。任务类型只加载需要的规划规则。 | 减少冗余输出及键不一致问题，降低额外规划调用概率；保留原始问题和全部用户硬约束。 |
| 每条分支都用模型选择相同或明显的来源 | 对精确文档标识、明确版本与唯一候选等确定情形先本地选择；复杂歧义仍由模型选择，可将互不越权的候选选择合并为一次批处理。 | 简单任务的 2–3 次选择调用有机会降到 0–1 次；仅省选择过程，事实资格仍由原文核验。 |
| 核验结束后，又单独发送长上下文让模型生成两条补查词 | 在现有核验输出中增加最多两项恢复建议，显式关联缺口需求；宿主重新过滤已覆盖项、重复查询和不可执行动作。只有方案根本变更或结构失败才独立重规划。 | 正常缺口恢复减少 1–2 次单独规划调用；对本题而言这是高价值的调用减少点。 |
| 每轮重新核验全部来源和全部需求，结果反复 | 引入受作用域约束的核验快照；同输入快照直接复用，新增材料仅触发相关需求核验。无法确认影响范围时回退全量。 | 减少重复阅读与全量输出，也降低同一材料反复得到不同结论的机会；不是跨任务复用任意旧结论。 |
| 提示词同时携带技术、科研、预算等无关规则；Schema 重复 | 以共有的来源/引用/约束规则为底，按研究类型和是否存在交付方案加载模块；普通核验只携带实际使用的输出结构和当前所需字段。 | 减少每次固定输入。当前 Executor 核验 Schema 的本地估算约 2043 token，属于值得检查的固定开销；不能声称这些估算等同供应商精确计费分摊。 |
| 页面无法读取仍换词重试，没有新增有效证据 | 根据 URL、文档版本、格式与失败类型记录恢复状态。体积/页数限制优先换合法格式或章节；有限重试后没有新可用原文则停止补查，给出具体阻断原因。 | 减少无收益的补查、来源选择和核验回合；不同于把缺口标成已完成。瞬态网络失败仍允许有限重试。 |
| 最终复核把整篇答案再生成一次，关键代码条件仍漏检 | 复用现有事实复核和重要结论审查代码，聚焦规范性结论、用户硬约束、引用及代码分支。返回问题位置和最小修订建议；语义性错误需要定向修订，无法确认时保留部分完成。 | 保留关键质量成本，减少整篇重写的重复输入/输出。审查次数不以模型“自信”作为跳过依据。 |

## 5. 推荐的新调用过程

以一个有界研究题、一次补查为例：

1. 一次规划：封存用户要求，生成互补任务和读取词。
2. 宿主搜索、抓取、章节检索及去重；来源存在歧义时才加模型选择。
3. 一次集中核验：输出有来源支持的发现、覆盖结论，以及有限的补查建议。
4. 宿主执行实际补读或搜索；对受影响需求做一次增量核验。
5. 一次起草，加一次关键结论/约束复核；发现关键语义错误时才追加定向修订。

这通常约 5 次基础调用，加上来源歧义、自动路由或必要修订后约 6–8 次。复杂多分支任务仍可更多，不把所有任务强压为 3 次。最终复核失败仍可能得到 partial；预算减少不改变事实覆盖的含义。

## 6. 核验复用的正确性约束

复用记录至少绑定：workspace/run、原问题与用户约束摘要、需求修订号、来源资格规则、来源 ID/版本/正文哈希、可见阅读范围、关联结论及其原文支持、模型与参数、提示/校验规则版本。

- 只有输入作用域相同且此前已验收的结果才能复用；失败或未核验结果不能作为通过缓存。
- 新材料涉及相同对象/条款、存在冲突、来源失效或正文变化，相关需求必须重新判定；作用域不清楚时回退全量。
- 来源范围、用户限制、模型或规则改变会使旧记录失效。不同租户/任务不共享结论。
- 引用始终指向实际原文；局部取段必须保留章节、否定、条件、代码块和完整语义组。
- 格式修复固定使用同一个可见原文快照和引用编号，避免更换窗口后沿用旧引用。
- 覆盖缓存是研究过程内的证据状态，不接入长期用户记忆。

## 7. 实施顺序与验收

### 阶段一：资料获取、简化规划、规则分模块

优先修改现有 `tools/scraper/fetcher.py`、`tools/scraper/pdf.py`、`tools/evidence_views.py`、`strategies/planning.py`、`harness/source_selection.py`。补上分段计量：提示规则、Schema、证据、历史状态的 token 估算与实际供应商 usage 分开记录；记录实际模型请求参数。

先证明大文档后半部分可以被检索，且单个任务仅携带相关规则。保留原有三种执行图、预算和引用校验。

### 阶段二：核验与恢复建议合并、快照复用

围绕 `strategies/evidence_evaluation.py`、`evaluation_materials.py`、`gap_recovery.py` 和三个策略的节点增量改造；复用已有工具缓存、补读与检查点机制。新恢复建议由宿主做目标、来源授权和去重校验，不能直接执行模型提出的任意操作。

### 阶段三：关键项复核与真实回归

调整 `responses/fact_review.py`、`claim_audit.py`、`graph.py`，让审查重点与原问题和代码条件对应。覆盖 HTTP 重试、Python 3.11 诊断、跨语言调查、简单事实题、来源变化/冲突和范围受限资料题，检查三种模式及检查点恢复。

不自动执行未知模型代码；伪代码的控制流使用结构化场景复核及人工验收。HTTP 题至少保留两个反例：无去重承诺的 POST 429 不得被当成已知未执行；Retry-After=120 秒且剩余 30 秒时应停止。

### 成本与质量目标

以当前 Plan-and-Execute 的 **11 次、50064 输入 token** 量级为参考，第一轮改造将有界题的目标设为 **6–8 次、25000–35000 输入 token**。这是待验证的工程目标，约 30%–50% 输入减少，不是已实测收益，更不是复杂任务的统一硬上限。

质量验收必须保留原题与来源约束，关键项通过率不下降，并修复现有已知关键错误。取得更多正确证据后输入可能增加，不能通过缩小题目或把 partial 改名为 complete 达标。

对照应先用同一批冻结来源测流程成本，再做真实网络运行；统一实际温度和其他请求参数。对关键样本重复运行，记录中位数、范围、失败率与缺口，冷启动和热请求分开计时。提示缓存若启用，另外报告命中量和计费口径。
