## 发现的问题

### 1. Baseline 输出截断，结构化结果未完成

两次回答的输出 usage 都为 2048 Token，原始响应均在句中结束，缺少完整 JSON 结尾。一次受控纠正后仍无法解析，正常应用链路保留为 `generation_failed`。证据已抓取，所以这不是网页抓取前的轮数耗尽。

后续要将报告长度要求与模型输出额度协调，或采用简短回答模式 / 显式更高的输出请求上限，并对双方保持相同条件；需要新实验身份，保留这次失败记录，不覆盖旧数据。本轮没有额外重试。

### 2. completed 不等于证据充分

Harness 最终选入的是 Threads / Checkpoints 摘录，却回答了跨线程 Store 等事实，且将这些事实都引用到同一编号。该摘录并不完整包含 Store 说明。Faithfulness 的 NLI 输出判定 25 条陈述中 12 条有证据支持，得到 12/25=0.48。

这说明研究的证据保留与最终答案引用边界仍有问题：不能让某段研究总结替代原始证据，也不能只检查引用编号存在。应该优先检查已抓取证据为何未进入最终 outcome，并增加逐条引用支持验证。

2026-10-02 续建更正：上段关于“已抓取证据未进入 outcome”的推测未获轨迹支持。完整工具结果表明三个分支重复抓取 Checkpoints 摘录，未抓取 Store 摘录，应归为检索覆盖与停止判定不足，而不是 Store 原文存储丢失。本轮未改动原始记录、答案、评分或证据。细节见 [续建报告](benchmark-continuation-20261002.md)。

### 3. Goal 裁判过于宽泛的风险

Goal=1 与事实 F1=0.50、忠实度=0.48 同时出现，表明本题的总体目标判定并不能替代事实完整性和证据支持。需要在后续多题开发校准与人工盲评中检查裁判一致性；不能把 Goal 指标称为最终“正确率”。

### 4. 请求输出上限不等于已验证的收费 Token 硬上限

评分端虽然请求 `max_tokens=2048`，部分实际 usage 高于该值（如 2636、4605）。目前未核实是否涉及 Provider 对参数/推理 Token 的不同口径，因此不臆测原因，也不把请求参数当实际计费 Token 的可靠硬上限。Provider 尝试数限额仍在 SDK 调用前强制检查。
