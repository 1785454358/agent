## 统计口径

来源：[records.json](../../tmp/grounded-handoff-live-answer-20261003/records.json)、[manifest.json](../../tmp/grounded-handoff-live-answer-20261003/manifest.json)。原始records文件SHA256：`e761aa8cf1d6045ecc2e2fa510aa14e884b2144e495ce4661b8f25a1144d01f3`。

- 一轮是一次研究员模型调用，不是一个工具，也不是整次用户任务。一轮可调用多个工具；模型传输重试另计Provider attempts，不自动多算研究轮。
- 用trajectory.model_turns中role=researcher按branch分组计数；本批每运行两个不同查询、无相同查询的多次补查，因此不会把不同分支实例合并。本批模型消息、总模型调用及Provider尝试数一致，未发现研究模型边界失败导致缺失返回轨迹。
- 工具轮类型按该轮实际请求分类：有search/fetch/read为研究工具轮；只有todo/record为纯本地工具轮；无工具为纯文本轮。混合轮是研究工具轮的子集，不能再次相加。
- 每题每模式一次，共1道题、3次运行、6个分支，不是6道题。冻结资料结果不混入主表，也不将旧无同口径分支轨迹的联网Workflow集成测试并入平均。

## 能得到和不能得到的结论

- 6/6分支观察到12轮且撞上配置上限，研究轮数观测最小值、最大值和均值均12；这是被上限截尾后的执行数，不是自然完成所需轮数。没有正常完成分支，成功分支轮数均值、P95及所需额外轮数均不可估计。
- 三次整任务均partial，且都有多个分支耗尽。不能用非空答案反推分支已经完成，也不能说一定需要24轮。
- P&E的CancelledError分支第12轮完成全部todo，当前协议仍需要一次无工具模型消息才可结束，说明可减少一类收尾开销；但另一分支8次read、0次record，不能只改完成状态就认为全任务解决。
- WF有6轮纯本地工具轮的分支，MA两个分支都8次read：问题不限于待办维护，也包括重复范围、阅读定位和迟迟不收尾。仅提高上限可能增加耗时与token。
- 一道联网题无法估计普遍所需轮数。下一步若确认实施，先在同样12轮及相同总额度下验证分工/收尾/输入视图效率；记录每个分支的自然完成轮数、失败/截尾状态和实际token。只有仍持续获得有效新证据却被截断时，才据新数据单独讨论提高上限。

当前实际配置仍为每分支12轮、每运行40 logical / 80 Provider / 24 Gateway / 360秒，全批次120 logical / 240 Provider。生产代码默认迭代上限仍8（实际环境可显式覆盖），本次两者均未修改。
