# DeepResearch 核心差异面试与学习文档设计

## 1. 目标

新增一份围绕单一母问题的学习与面试文档：

> 你做的 DeepResearch 和市面上成熟的 DeepResearch 项目，核心区别是什么？

文档不重复现有《开源深度研究项目对比面试问答》的逐项目百科式内容，而是训练候选人用同一套核心定位完成 30 秒、90 秒和 5 分钟回答，并承受连续压力追问。

回答采用“先承认成熟方案优势，再建立自己的差异坐标”的姿态。重点展示更有价值的设计方向，但不虚构 benchmark、线上收益或并未完成的实现证据。

## 2. 目标读者与使用场景

目标读者是准备 Agent 开发、大模型应用工程岗位面试的项目作者。

文档用于：

- 第一次回答“为什么还要自己做 DeepResearch”；
- 面试官继续追问架构、可靠性、评测和实现边界；
- 对比通义 DeepResearch、LangChain open_deep_research 与 gpt-researcher；
- 面试前按差异点补知识、准备 Trace 和验证证据；
- 识别强势表达与夸大表述之间的边界。

## 3. 核心定位

全文围绕以下中心观点展开：

> 成熟 DeepResearch 项目主要竞争“研究结果做得多好”，本项目更关注“开放式研究过程如何在真实工程环境中受控运行”。不声称模型能力天然更强，差异在于把策略、上下文、工具、副作用、恢复、证据和退出统一成可验证的 Harness 协议。

核心差异拆为五个维度：

1. **目标不同**：成熟项目优先答案质量、搜索能力与开箱即用；本项目优先可控、可恢复、可审计、可比较。
2. **分层不同**：策略负责如何拆任务，Shared Harness 负责如何执行；三种策略共享同一运行协议。
3. **状态不同**：Evidence、Outcome、Checkpoint、Ledger 是一等对象，不只保留最终文本。
4. **失败不同**：transport retry、semantic repair、recovery replay 有明确所有者，外部副作用先核对再重放。
5. **评测不同**：除答案质量外，同时检查证据覆盖、调用成本、终止原因、恢复和错误副作用。

## 4. 文档结构

文件：`docs/resume/DeepResearch核心差异面试与学习手册.md`

### 4.1 母问题与答题策略

先解释面试官真正想判断的内容：是否了解竞品、是否有独立设计判断、项目是否只是复刻、是否能诚实说明边界。

给出统一答题公式：

```text
承认对方优势 → 说明目标不同 → 给出三项结构差异 → 提供一个工程例子 → 主动收住事实边界
```

### 4.2 三层标准回答

- **30 秒回答**：一句定位、三个差异词、一个边界。
- **90 秒回答**：成熟项目优势、Harness 定位、三项核心设计、验证方式。
- **5 分钟回答**：从任务目标、分层架构、Context、Tool、恢复、Evidence、Outcome 和 Eval 完整展开。

三层回答必须共享同一观点，不能出现不同版本互相矛盾。

### 4.3 五个核心差异

每个差异使用同一格式：

- 成熟项目常见做法；
- 本项目选择；
- 为什么值得做；
- 代价与适用边界；
- 面试中的一句话表达；
- 继续追问时需要准备的证据。

### 4.4 三个点名追问

- **通义 DeepResearch**：模型训练、合成数据和 benchmark 能力，与运行时治理的差别。
- **LangChain open_deep_research**：成熟框架模板、可配置性和公开实验，与统一治理协议的差别。
- **gpt-researcher**：开箱即用研究产品和固定 pipeline，与可恢复、可审计 Harness 的差别。

点名回答以定位差异为主，不堆未经重新核实的版本细节和具体 benchmark 数字。需要引用对方当前实现时，应以官方仓库或论文为准；本文本身不承担竞品事实数据库职责。

### 4.5 压力追问链

至少覆盖：

- 你的答案质量凭什么更好？
- 这是不是过度工程？
- LangGraph 已经有 Checkpoint，你还做了什么？
- 三种策略是不是为了堆功能？
- 这些亮点哪些真正实现了？
- 如果删掉 LangGraph，还剩下什么？
- 如果重做，最先砍掉什么？
- 为什么成熟项目没有这些设计？
- 运行时治理会不会拖慢研究质量和速度？

每个回答先正面回应，再说明取舍，最后给出可验证证据或事实边界。

### 4.6 强势但安全的表达

使用三列表格：

| 推荐说法 | 容易翻车的说法 | 被追问后的收口 |
| --- | --- | --- |

重点纠正以下风险：

- 不说“研究质量优于成熟项目”，除非有同口径 benchmark；
- 不说“解决了 Prompt Injection”，只说已有 URL/SSRF 与工具边界，内容级防护仍需补齐；
- 不说“保证 exactly-once”，只说降低 at-least-once 下的重复影响；
- 不把离线测试写成线上质量；
- 不把设计完整性直接说成生产成熟度。

允许突出“我的设计重点”“完整方案中的关键机制”“我会如何验证”，但涉及已实现与实测结果时必须可回到项目证据。

### 4.7 学习与训练

按五个差异维度列出：

- 必须理解的概念；
- 推荐阅读的项目材料；
- 应准备的架构图、Trace、测试或实验；
- 一道基础追问和一道压力追问；
- 能否过关的判断标准。

最后提供一轮 15–20 分钟模拟面试脚本和评分表。评分维度包括定位清晰度、技术深度、取舍意识、证据意识、事实边界和表达节奏。

- `Agent Harness面试手册.md` 继续负责 Harness 内部技术追问。
- `Agent Harness学习与面试路线.md` 继续负责完整源码学习和实验路径。
- `Agent Harness实现差距与完善清单.md` 继续负责当前实现状态和开发优先级。

新文档通过链接引用这些材料，不复制其完整内容。

## 6. 写作风格

- 以可直接复述的中文口语为主，避免论文式长句。
- 先给结论，再给解释和例子。
- 每个标准回答都能独立使用，不依赖读者先读其他章节。
- 强调“目标不同、评价坐标不同”，避免贬低成熟项目。
- 承认模型能力、生态、数据与 benchmark 的现实差距，突出运行时治理和实验方法的独立价值。
- 不写成背稿模板；每段回答后解释其结构和追问入口。

## 7. 验收标准

- 文档只围绕一个母问题展开，且 30 秒、90 秒、5 分钟回答观点一致。
- 五个差异维度均包含价值、代价、边界和证据要求。
- 三个点名对比均先承认对方优势，再说明目标差异。
- 至少包含九个压力追问及可直接复述的回答。
- 至少包含八组“推荐说法 / 翻车说法 / 收口方式”。
- 学习部分包含可执行的证据准备任务和模拟面试评分表。
- 不出现无法验证的 benchmark、线上收益或绝对优越性结论。
- 与现有比较文档、面试手册和差距清单互相链接且不重复大段内容。

## 8. 非目标

- 不重写完整竞品调研报告。
- 不更新或验证所有竞品的最新功能与 benchmark。
- 不为了回答漂亮而虚构当前项目已完成的能力。
- 不修改后端实现或补齐项目缺口。
- 不新增配图；本任务重点是回答结构、学习训练和表达边界。

## 9. 工作区保护

当前工作树存在用户的未提交修改。实施时只新增目标文档，并在资料索引中添加入口时保留已有内容；不得重置、覆盖或提交无关修改。
