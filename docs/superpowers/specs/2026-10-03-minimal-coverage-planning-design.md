# 第三轮：最小覆盖规划

## 用户选择与目标

用户在最小覆盖规划、阶段预算预留、短引用标签三个方向中选择 A：优先 1–3 条查询覆盖问题，合并近义任务，不把搜索、提取、汇总分别拆成研究分支，不删必要答案要点。

本轮只调整三模式共用的初始规划提示，不增加调度器、辅助模型调用、服务、状态或依赖。主验收为 Plan-and-Execute + Answer；Workflow、Multi-Agent 同条件复测，Report 不合并评分。方向已选择，具体书面规格仍需用户审阅。

## 根因与假设

上一批 `todo-progress-real-answer-20261002` 为 3 completed / 3 partial / 3 failed。三条失败均触发评测的 RequestLimitReached：1 次初始规划 + 39 次研究，未进入 evaluator/responder。

- P&E 版本题生成 6 条近义查询，将两个主题分别重复为普通限制和版本专有限制，形成 4 条重复答案要点。
- MA 版本题生成 5 项 assignment，包括检索、提取同一主题和最后汇总；MA 多跳题也独立派出“核验是否符合文档”的泛化过程任务。
- `planning_instruction` 当前只要求“互不重复”“最多 limit 条”，没有说明这是上限而不是目标数量，也没有明确将过程任务留在已有研究循环/评估/回答阶段。现有字符串去重不能识别近义表达。

可检验假设：明确最小覆盖、互补分工和事实/过程边界，可以减少重复初始分支，为评估与回答留下更多实际调用机会。它不是确定性语义去重或运行级预算预留，不保证消除失败、覆盖完整或评分提高。

## 选择与替代方案

1. **已选 A：共享最小覆盖提示。** 范围小，复用现有组件，不增加复杂度；真实效果依赖模型。
2. 阶段预算预留。能限制研究占用收尾额度，但涉及生产计量、并发及 checkpoint 恢复，本轮不做。不能只改评测包装器就称为生产预算治理。
3. 短引用标签。针对上一批 passage_id 抄写错误，但不能解决初始研究分支占尽调用，本轮不做。

## 具体设计

唯一生产修改点为 `backend/src/deeptrace/strategies/planning.py` 的 `planning_instruction(query_field, limit)` 返回文本。三个初始规划节点已经调用它，无需新增接口。

### 数量与覆盖

- 先从完整原始问题识别既有有界契约内的独立答案要点；保留显式子问题及完整回答必需的事实边界，不自行添加额外验收条件。
- 合并同一事实的不同问法，不将相同版本条件下的同一问题再重复列成“版本专有问题”。版本或法律边界若本身是用户询问的事实，仍必须研究。
- 选择覆盖全部答案要点的最少互补查询。优先 1–min(3, limit) 条；只有确有更多独立研究问题需要时，才能增加到既有 limit。limit 是硬上限，不是应凑满的数量。
- 1–3 不是新的硬上限：不得在宿主把合法计划裁成三项，也不能为了减少分支丢弃问题。一个查询可覆盖多个相关答案要点，查询与 requirements 不要求一一对应。

### 研究分工与既有阶段

- queries/assignments 描述需要获取证据的互补事实问题，而不是一串流程动作。
- 不把同一事实的“检索→提取→核验已有结论→汇总写作”分别派成独立初始研究任务；具体工具步骤留在已有 Agent loop，覆盖/原文支持核验与最终回答留在已有 evaluator/responder。
- 若用户问题本身要求核实一个有争议的事实或比较独立证据，它仍是合法研究问题；不把“避免泛化过程任务”误解为禁止事实核查。
- 保留事实 requirements 与 execution_constraints 分区、完整原始任务、用户约束和不可信来源边界。不给模型新的工具权限、访问范围或预算。

### 兼容、异常与排除项

初始默认上限仍为 P&E 6、MA 5、Workflow 3；requirements 仍为 1–6。JSON 输出字段、参数、解析/去重、封存需求、坏规划回退原问题及旧缺省 metadata 兼容保持不变。

坏规划回退的发现查询仍按现有逻辑最多保留原问题前 1000 字符；完整原始任务另行固定传入，不能声称本轮改变了该发现查询上限或将截短查询当完整完成标准。

不修改补查/replan/follow_up、待办更新契约、执行策略、预算/重试/分支轮数、URL 或证据授权、来源选段、引用标签、原文支持门禁、强退出规则、持久化/checkpoint schema、模型或 Ragas 标准。不做 embedding 语义聚类、宿主自动合并/删除模型事实要求，也不添加针对三道开发题的特判或参考答案内容。

## 验收

1. TDD 先通过三个真实初始规划节点捕获外部模型实际收到的提示，验证最小覆盖、互补事实、过程任务不独立派发与完整任务/约束；传入 limit 为 1 或 2 时，优先范围不能超出 limit。指令消费测试只验证接口契约，不证明模型会减少分支。
2. 真实节点保护回归：当传入 limit≥4 时，四项合法独立查询及对应事实要求不被硬裁成三项；默认上限、非法 metadata/JSON 回退、旧 metadata 缺省、需求封存与原始约束不变。
3. 运行已有规划、补查、三模式、待办、证据支持及 checkpoint 恢复回归；冻结源码/HEAD 跑完整后端 `pytest -m 'not real'` 和隔离 `evaluation/tests`。在 backend 工作目录做定向 Ruff，不修无关旧 lint。
4. 真实轨迹同时报告初始查询/assignment 数、实际研究分支数、重复/过程性任务的审查依据、各角色调用、纯待办轮、completed/partial/failed、非空答案、Provider/工具/Token 和质量有效覆盖。实际进入的分支不等于初始规划总数；不可只统计完成或可评分样本。

## 书面确认后的真实 API 边界

沿用已授权的小规模同条件复测：同三道已用 dev 题（single_hop-dev-01、multi_hop-dev-02、version_boundary-dev-02）、同 7 篇冻结官方语料，三模式每题各一次，共 9 条 Answer。资产复用 `tmp/evidence-loop-real-20261002-assets/`，gold 只进入评分侧。

模型 doubao-seed-2.0-lite / temperature=0 / 输出最多 4096 token / Answer 最多 2000 字符 / 长时记忆关闭。单运行最多 40 逻辑调用、80 Provider 尝试、24 工具入口、12 分支轮、360 秒；整批最多 360 逻辑 / 720 Provider 尝试。隔离 Ragas 0.4.3 原模型、scorer 与输入限额，最多 144 次评分 Provider 尝试。

唯一批次及目录：`tmp/minimal-plan-real-answer-20261003/`、`tmp/minimal-plan-real-answer-quality-20261003/`、`tmp/minimal-plan-real-answer-comparison-20261003/`。付费前登记并核对规范化数据哈希、配置和目录不存在；如果已存在或发生不明确中断，先检查，不自动换目录重新调用。完整离线回归和真实批次期间冻结源码/HEAD，逐文件保存并校验 source_snapshot；本轮新回归测试单独留样。

不新增 baseline、不运行未见 test split、不扩预算、不改 gold/评分、不裁短评分正文、不自动重跑失败或重评挑高分。与上一批逐题同模式对照仅为开发诊断；不同可评分覆盖均值不可当作因果效果。三题无重复且经过调试，同模型裁判、短参考/claim 粒度敏感性及独立人工复核为 0 的限制仍保留；这不是生产实时联网 E2E，不能预先保证 completed 或事实质量提高。没有新 baseline，配对 n=0、delta/CI=null。
