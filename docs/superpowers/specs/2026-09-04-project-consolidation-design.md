# DeepTrace 项目收口设计

- 日期：2026-09-04
- 状态：已完成
- 当前分支：`main`

## 1. 目标

将当前工作区已经完成但尚未提交的新架构整理为可回归、可提交、可继续进入阶段 6 的稳定基线。

当前架构以阶段 1 至 3 的规划式研究链路和阶段 5 的产品化能力为准。阶段 4 的 Evidence Store、Claim Extractor、Verifier 已经由项目所有者决定移除，本次不恢复相关源码、状态字段、提示词或测试。

## 2. 当前能力边界

保留并提交以下能力：

- Planner 将问题拆分为互补研究任务。
- Researcher 通过真实 Tavily 搜索和网页抓取获取材料。
- 本地 BGE-M3 完成召回和零 LLM 的原句压缩。
- 多个研究任务通过有界并发执行，并共享页面、时间、步骤和可选费用安全边界。
- Writer 消费带来源编号的原句笔记，引用编号由程序校验和拼接。
- FastAPI 提供任务创建、查询、取消和 SSE 事件流。
- 运行结果持久化到本地 `runs/`，可选 Research Memory 复用已抓取页面。
- Token 只做分阶段统计，不再作为停止条件。

本次不实现阶段 6 的固定评测集、数据库、账号体系、部署或新的事实核验 Agent。

## 4. 验证

自动化验证依次执行：

1. `uv lock --check`
2. `uv run pytest -m "not real"`
3. `uv run python -m compileall -q src tests`
4. `uv run deeptrace --help`
5. `git diff --check`

真实回归原则上只执行一次：启动 FastAPI，通过 `POST /researches` 创建真实研究任务，轮询到终态，并检查任务事件、最终报告、来源、分角色 Token 和 `runs/<id>.json` 持久化结果。若真实回归暴露阻塞性缺陷，则按系统化调试流程修复后允许复测。该运行使用现有真实 LLM API、Tavily、网页抓取和本地 BGE-M3。

CLI 的完整输出契约由自动化测试覆盖，不再额外执行第二次真实研究。真实运行可以得到 `completed` 或诚实的 `partial`；`failed`、进程崩溃、空报告、无持久化记录或未到达 Writer 均视为回归失败。

## 5. 提交策略

最终形成三个逻辑提交：

1. 本设计规范。
2. 后端新架构、API、Memory、测试、依赖与忽略规则。
3. 文档状态统一、废弃历史标记、问题记录、旧资料与参考实现清理。

真实日志、运行报告、Memory 正文和 `.env` 不提交。提交前检查暂存文件清单和敏感信息，确保工作区中的有效改动全部进入上述提交或被明确归类为本地生成物。
